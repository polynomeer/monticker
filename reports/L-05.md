# L-05 order-burst — 동시 주문 부하 하의 자금 정합성 검증

> **페이퍼 트레이딩 규모 개인 프로젝트, 로컬 한 대 측정 — 절대 처리량이 아니라 정합성·상대 비교용.**
> [ADR-045](../docs/decisions/045-performance-slo-and-verification-harness.md) §3(정합성 검증 하네스)·§5(거래 클래스 SLO)의 구현.
> scale-out-plan Phase 0의 마지막 항목(0.8)에서 빠져 있던 "정합성 검증"을 채운다.

- 부하: [`bench/scenarios/order-burst.js`](../bench/scenarios/order-burst.js) (k6)
- 검증: [`bench/consistency/verify.py`](../bench/consistency/verify.py) — 부하와 독립적으로 DB 재계산 대조(psql만 사용)
- 실험일: 2026-09-17

## 1. 목적

ADR-045 §3: "부하를 견뎠는가"가 아니라 **"부하 중에 틀리지 않았는가"**를 본다. 거래 클래스 SLO는 성능이 아니라 **자금 정합성 오차 0**이
본체다(§5). 동시 주문을 몰아친 뒤, 원장 불변식·체결 무결성·Saga 잔류를 독립 재계산으로 대조한다.

## 2. 방법

- 각 k6 VU = 독립 계정(`burst-<RUN>-<vu>@bench.local`, `X-Bench`로 IP 레이트리밋 우회). VU마다 고정 종목 하나를 시장가로 거래(3 BUY : 1 SELL).
- 검증(`verify.py`, [ADR-043](../docs/decisions/043-ledger-pagination-and-reconciliation.md) 대사 로직 재사용):
  - **잔고 불변식**: 계정마다 `cash + reserved == 10,000,000 + Σ ledger.amount[현금 이벤트 타입]` (드리프트 0)
  - **체결 무결성**: `orders.filled_qty == Σ fills.quantity` per order, 중복 `fill_id` 0
  - **Saga 잔류**: `order_sagas` STARTED/COMPENSATING 0
- 환경: api `-Xmx2g`(Hikari 풀 20, connection-timeout 3s), Postgres/Redis/Kafka/Mongo(대체 포트). 로컬 한 대.

## 3. 결과

| VUs | 체결 | 거절(4xx) | 에러(5xx) | http p95 | 잔고 드리프트 | 중복 fill | Saga 잔류 |
|-----|-----|----------|----------|---------|------------|----------|----------|
| 40  | 200 | 925 | **1** | 76ms | **0** | 0 | 0 |
| 100 | 500 | 2,004 | 584 | — | **0** | 0 | 0 |
| 100 (재현) | 500 | 1,842 | 184 | **3,013ms** | **0** | 0 | 0 |

전체 400계정·2,000체결 종합 검증: **드리프트 0, 중복 fill 0, Saga 잔류 0 — PASS.**

- **거절(4xx)은 정합성 위반이 아니다**: 대부분 `TradingFrequencyRule`(계정당 ~5거래 후 422 — 리스크 가드레일, 정상)과 보유 없는 SELL(422).
- **핵심 결과 — 자금 정합성은 스트레스·장애 하에서도 유지된다**: VUS=100에서 커넥션 풀 고갈로 **584건이 5xx로 실패했는데도 잔고 드리프트 0**이었다.
  실패한 주문은 **원자적으로 실패**한다 — 부분 자금 이동도, Saga 누수도 없다. 이것이 이 실험의 본체다.

## 4. 발견

### 4.1 커넥션 풀 고갈 임계 (scale-out-plan §3.8 실증)

VUS=100에서 5xx 184~584건, http p95 **3,013ms**(= Hikari `connection-timeout` 3초 그대로 — CPU가 아니라 풀 대기다). VUS=40에서는 5xx 1건, p95 76ms.
즉 **동시 주문 ~100에서 풀(20)이 고갈**된다. 주문 트랜잭션 하나가 매칭+원장+Saga를 한 트랜잭션으로 묶어 커넥션을 오래 잡기 때문이다.
이는 [scale-out-plan §3.8](../docs/scale-out-plan.md)이 이미 지목한 병목의 **실측 트리거**다 — 대응(PgBouncer + 풀 축소)은 Phase 1(§6.3.1). 지금 규모(페이퍼)에선 실사용 영향 없음.
> Mongo 미기동 시엔 5xx가 7건뿐이었는데 Mongo 기동 후 급증했다 — 주문 경로가 JDBC 트랜잭션을 잡은 채 외부(Mongo) 호출을 하며 커넥션 보유 시간을 늘리는지는 §5의 조사 대상으로 남긴다.

### 4.2 존재하지 않는 stockId 주문 → 500 (경미)

시드 종목 id는 연속이 아닌데(202종목이 2~207에 구멍) 없는 id(7·8)로 주문하면 `risk_check_logs_stock_id_fkey` FK 위반이 500으로 샌다.
정상 사용(프론트는 유효 id만 전송)엔 영향 없으나, 주문 경로가 종목 존재를 먼저 검증해 400/404로 돌려주는 게 낫다 — backlog에 경미 항목으로 기록.

### 4.3 하네스 설계 메모

`@RateLimited(30/60s)`(matching orders AOP)는 `X-Bench`를 존중하지 않는다(`RateLimitFilter`와 비대칭). 부하 시나리오는 계정당 주문을 페이싱(SLEEP 2.5s)해 이 한도 밑으로 맞춘다 — 처리량은 계정 수로 늘린다.

## 5. 남은 것

- 4.1의 Mongo 상관(JDBC 트랜잭션 중 외부 호출로 커넥션 장기 보유 여부) 조사.
- 절대 처리량·SLO 판정은 전용 부하 환경([backlog §9](../docs/engineering-backlog.md))에서. 로컬 수치는 상대 비교·정합성 검증용.

## 6. 재실행

```bash
# 인프라 4종(postgres/redis/kafka/mongo) + api 기동 후:
IDS=$(docker exec monticker-postgres psql -U monticker -d monticker -tA -c "SELECT id FROM stocks ORDER BY id LIMIT 30" | paste -sd, -)
RUN=$(date +%s)
k6 run --env RUN=$RUN --env VUS=100 --env DURATION=90s --env SLEEP=2.5 --env STOCK_IDS="$IDS" \
  --env BASE_URL=http://localhost:58080 --summary-export reports/L-05/l05-summary.json bench/scenarios/order-burst.js
python3 bench/consistency/verify.py "burst-$RUN-%@bench.local"
```
