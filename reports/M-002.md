# M-002 — market.ticks 파티션 수 × 컨슈머 수에 따른 처리량·지연·종목별 순서 보장

> **페이퍼 트레이딩 규모의 개인 프로젝트다. 여기 숫자는 로컬 한 대(호스트 JVM/Go 프로세스 + Docker VM 안의 Kafka/Redis/Postgres)에서
> 잰 것이고 실제 운영 트래픽 검증이 아니다.** 조건당 3회 반복, 분위수는 p50/p95/p99, 평균은 쓰지 않는다.

- 대상 커밋: `8b30ca7` (계측), 실험 스크립트: [bench/experiments/](../bench/experiments/README.md) `m2-*.sh`
- 원본 데이터: [`M-002/raw/`](M-002/) — 조건·회차별 worker 스냅샷 JSON, 프로세스 샘플, summary.tsv, 로그
- 실험일: 2026-09-16

## 1. 목적

블로그 Track M · M2 의 세 질문에 답한다.

- (a) `market.ticks` 파티션 P ∈ {1, 3, 6, 12} × 컨슈머 C ∈ {1, 3, 6} 에서, 202종목 · 총 ~2,000 tick/s 고정 부하의
  처리량, e2e p95/p99, **종목별 순서 위반 건수**는 어떻게 달라지는가. 키=stockId 와 라운드로빈(키 없음)은 무엇이 다른가.
- (b) 컨슈머 리밸런스(worker 프로세스 SIGKILL → 재기동) 중 순서 위반·중복·유실은 얼마나 나는가.
- (c) 핫 종목 하나가 폭주할 때 같은 파티션의 다른 종목이 얼마나 밀리는가(head-of-line blocking).

## 2. 방법

### 2.1 부하 모델과 계측

- 발행: Go `market-gateway` — DB 의 활성 202종목마다 고루틴 1개, `TICK_INTERVAL_MS=100` → **≈ 2,020 tick/s**.
  실험 스위치(기본 꺼짐): `TICK_SEQ=true` 종목별 단조 seq(1, 2, 3…), `TICK_KEY_MODE=none` 키 없이 발행(kafka-go `Hash`
  밸런서는 nil 키만 라운드로빈), `TICK_HOT_STOCK_ID`/`TICK_HOT_INTERVAL_MS` 핫 종목.
- 소비: worker 1프로세스(기본 프로파일 + `experiment` 프로파일), `TickKafkaConsumer`(Redis 최신가 → 캔들 집계 → 이벤트 감지),
  `KAFKA_CONSUMER_CONCURRENCY=C` = 리스너 스레드 수. **C 는 스레드 수이지 프로세스 수가 아니다**((b)만 2프로세스).
- 관측: `experiment` 프로파일의 `TickOrderMonitor` 가 컨슈머가 받는 순서 그대로 종목별 seq 를 대조한다.
  - violation: seq < 그 종목의 지금까지 max (뒤바뀜) · dup: 이미 본 seq (재전달) · gap: seq > max+1 (그 사이 seq 수. 나중에 오면 violation 으로
    잡히므로 **유실 ≈ gap − violation**)
  - e2e = 틱 `generatedAt`(게이트웨이) → 컨슈머 수신. 같은 머신이라 시계가 같다. 전수 샘플에서 정확한 분위수.
  - 프로세스: actuator `process.cpu.usage`(×10코어 = 사용 코어), `jvm.memory.used`, `jvm.threads.live` 5초 샘플.
- 절차(조건마다): worker 재기동 → `market.ticks` 삭제·재생성(P) → **워밍업 20s**(JIT 전 첫 실행은 p50 이 10배 이상 높았다 —
  §4.4) → 3회 × [모니터 리셋 → 게이트웨이 40s → 정지 → 컨슈머 그룹 랙 0 대기 → 스냅샷].

## 4. 분석

### 4.1 D-M2-01 — 키가 같아도 순서가 깨졌다: 게이트웨이가 acks=0 이었다

수정 전 격자(§3.1)에서 키=stockId 인데도 **P>1 의 27회 중 9회에서 30–335건의 순서 위반**이 났고, P=1 에서는 9회 모두 0이었다.
모든 경우 위반 수 = gap 수, 중복 0 — 유실이 아니라 **같은 파티션 안에서 배치가 뒤바뀐 것**이다. Kafka 로그를 직접 읽으니
(스모크 실행, 파티션 2, `kafka-console-consumer --partition 2 --offset 2150`):

```
offsets 2208-2276 seq=33 n=69  ts=…07.402
offsets 2277-2336 seq=35 n=60  ts=…07.622   ← seq 35 배치가
offsets 2337-2405 seq=34 n=69  ts=…07.532   ← seq 34 배치보다 먼저 적재됐다
```

컨슈머는 한 파티션을 한 스레드가 순서대로 읽으므로 이건 프로듀서 쪽이다. 원인: `kafka-go` `Writer` 의 `RequiredAcks` 기본값이
**`RequireNone`(acks=0)** 이고([writer.go:150](https://github.com/segmentio/kafka-go/blob/v0.4.47/writer.go)) `producer.go` 가 그것을
명시하지 않았다. 브로커 응답을 기다리지 않으니 파티션 라이터가 다음 배치를 바로 보내고, 두 요청이 서로 다른 커넥션으로 나가면
브로커가 나중 것을 먼저 적재한다. 같은 이유로 브로커가 죽어도 프로듀서는 실패를 모른다 — **acks=0 은 조용한 유실**이기도 하다(M-001(b)).

수정: `RequiredAcks: RequireAll`(복제 계수 1인 로컬에서는 acks=1 과 같고, 운영 RF≥2 에서 맞는 값), 실험 재현용 `KAFKA_REQUIRED_ACKS=none`.
수정 후 격자(§3.2) **키=stockId 36회 전부 위반 0**. 비용: e2e p50 은 조건별로 −5 ~ +9ms 로 차이가 없고(§3.1 vs §3.2), 종목당 발행률 상한이
생겼다(§4.6).

### 4.2 키=stockId vs 라운드로빈 — 위반은 파티션 간 랙 차이가 틱 간격을 넘을 때만 보인다

라운드로빈(키 없음, §3.2 아래 3행)은 9회 중 7회에서 위반이 났지만 **3–27건**에 그쳤다. 종목당 틱 간격이 100ms 인데 파티션 간 처리 시점
차이는 보통 수십 ms 라, 같은 종목의 연속 틱이 다른 파티션에서 뒤집힐 기회가 드물다. 그러나 핫 종목(2ms 간격 요청 → 실제 ~11ms 간격)을
라운드로빈으로 뿌리자 **84–172건**(§3.4 `hot-none`)으로 뛰었다 — 위반이 거의 전부 핫 종목에 몰렸다(`stocks_affected` 0–5).
결론: 라운드로빈은 "보통은 괜찮아 보이지만" 빠른 종목에서 곧바로 깨진다. 키=stockId 는 acks 를 고친 뒤 45회 0건. 이 저장소의 결정(ADR-005:
키=stockId)은 맞고, 다만 acks 없이는 키만으로 부족했다.

### 4.3 D-M2-03 — worker 하나가 죽으면 그 파티션은 45초, 살아남은 쪽도 17초 멈춘다

§3.3 수정 전: 유실 0·중복 0·위반 0 은 좋은 소식이다(at-least-once 가 실제로 동작하고, 커밋 간격이 짧아 재전달도 없었다). 나쁜 소식은 시간이다.
- w2 가 맡던 3개 파티션(전체 틱의 절반, 49,500–50,490건)이 **45.0초** 동안 아무도 읽지 않았다. 3회 모두 45,035–45,045ms — Kafka 3.x
  컨슈머의 `session.timeout.ms` 기본값 45,000ms 그대로다. SIGKILL 된 멤버는 LeaveGroup 을 보내지 못하므로 코디네이터가 세션 만료까지 기다린다.
- 더 나쁜 것: +20s 에 대체 프로세스가 합류하자 **생존자 w1 이 자기 파티션까지 전부 내려놓고(eager 프로토콜의 revoke-all) 세션 만료까지 17–18.5초
  아무것도 처리하지 않았다** (`w1_stall_max_ms`, w1 로그 `Revoke previously assigned partitions market.ticks-1,3,5` → 18.5s 뒤 `Successfully joined`).
  즉 크래시 하나가 **시세 전체를 멈춘다**. K8s 의 정상 종료(SIGTERM → LeaveGroup)는 이 경로가 아니지만 OOM-kill·노드 장애는 이 경로다.

수정(`KafkaConfig`): `session.timeout.ms=10000`, `heartbeat.interval.ms=3000`(Kafka 3.0 이전 기본값), `CooperativeStickyAssignor`.
수정 후 3회: 인계 공백 10.6–12.5s(세션 10s + 리밸런스), **생존자 정지 111–287ms**, 유실·중복·위반 여전히 0. 생존자의 자기 파티션 p99 가
kill 후 50초 창에서 1.4–1.6s 인 것은 인계받은 파티션의 10초치 밀린 틱을 같은 스레드 풀(C=3, 이제 파티션 6개)로 소화하는 동안의 경합이다.
남은 10초는 세션 타임아웃의 본질이라 더 줄이려면 heartbeat 를 더 촘촘히 하거나(GC 정지에 취약) 정적 멤버십(`group.instance.id`)으로 가야 한다.
운영 주의: eager → cooperative 전환은 롤링 배포 시 두 단계(양쪽 어사이너 나열 → cooperative 만)로 해야 한다(Kafka 문서).

### 4.4 P × C — 어디에 두어야 하나

- **처리량은 어느 조건도 병목이 아니었다.** 12조건 모두 입력 2,015 tick/s 를 그대로 처리했고 worker CPU 는 0.2–0.3 코어. 이 부하에서 P·C 가
  가르는 것은 처리량이 아니라 **꼬리 지연**이다.
- P=1: p99 가 288–1,578ms 로 가장 나쁘고 C 를 늘려도 나아지지 않는다(파티션 1개는 스레드 1개만 쓴다 — C=6 이어도 246개 스레드 중 1개가 일한다).
- C=1: P 를 늘려도 p50 40–56ms, p99 260–1,918ms 로 P=1 과 비슷하다 — 파티션은 병렬성의 상한이지 병렬성 자체가 아니다.
- **P=6·C=6 이 가장 낮다**: p50 20–21ms, p99 59–64ms(수정 전) / 115–484ms(수정 후, 1회 스파이크 포함). P=12·C=6 은 p50 이 같고 p99 는
  107–224ms 로 P=6 보다 못하거나 같다 — 202종목을 12개로 쪼개면 파티션당 배치가 작아지고 스레드당 파티션 2개를 번갈아 폴링한다.
  이 부하에서는 **파티션 수 ≈ 스레드 수 ≈ 6** 이 답이고, ADR-040 의 로컬 12·운영 64 는 "미래의 틱 레이트" 를 위한 여유지 지금 성능을 위한 값이 아니다.
- **꼬리 스파이크(p95 1.5–2.6s)가 3회 중 1회꼴로 아무 조건에서나 났다**(P1C6 r1, P3C1 r3, P6C1 r3, P6C3 r1 …). 분 경계에 202종목의 1분 캔들을
  리스너 스레드에서 동기 upsert 하는 `CandleAggregator.onTick → flush` 를 의심했지만, 실행 창이 분 경계를 넘은 53회 중 16회 vs 넘지 않은 19회 중 5회로
  차이가 없어 **증명하지 못했다**. 원인 미확정으로 남긴다. 어느 쪽이든 §4.3 실시간 SLO(p99 300ms)를 P6C6 도 안정적으로는 못 지킨다 — 이 스파이크가 다음 실험 대상이다.
- worker 스레드 수가 C 에 정비례로 커진다(C=1 86, C=3 152, C=6 251): `@RetryableTopic` 이 리스너마다 본토픽+retry-0+retry-1+dlt 컨테이너를 만들고
  각각 C 스레드를 갖는다. 3개 리스너 × 4 컨테이너 × C. 지연에는 영향이 없었지만 운영 스레드 예산에 넣어야 한다.

### 4.5 D-M2-02 — 게이트웨이가 SIGTERM 에 멈춘다

첫 격자가 P1C3 워밍업에서 28분간 멈췄다. 게이트웨이가 SIGTERM 을 받고 `shutting down` 을 찍은 뒤 `defer producer.Close()` 에서 영원히 기다렸다.
goroutine 덤프(`raw/…/gateway.log`): `Writer.Close → sync.WaitGroup.Wait`, 그리고 `partitionWriter.writeBatches → batchQueue.Get → sync.Cond.Wait` 하나가
"created by (*Writer).spawn in goroutine 65" — 종목 고루틴이 ctx 취소 뒤에도 `WriteMessages` 를 한 번 더 부르고, kafka-go 는 `closed` 검사 뒤 뮤텍스를
놓았다가 `batchMessages` 에서 **Close 가 비운 맵에 새 파티션 라이터를 만든다**. 그 고루틴의 큐는 아무도 닫지 않는다(kafka-go 의 경합, 우리가 유발).
수정: `generator.RunWith` 가 `WaitGroup` 으로 종목 고루틴 종료를 기다린 뒤에야 돌아오고, 그 다음 `Close`. 수정 후 격자 51회 + (b)(c) 24회에서 재발 없음.

### 4.6 부수 관찰 — 종목당 발행률 상한 ~90/s

acks 를 켜자 종목 고루틴의 동기 `Publish` 가 배치 왕복마다 한 건이 됐다: `TICK_HOT_INTERVAL_MS=2` 를 줘도 3,590–3,660 틱/40s ≈ **90/s**.
BatchTimeout 10ms(ADR-045 때 1s → 10ms 로 낮춘 값) + RTT 다. 실제 KIS/Toss 체결가는 종목당 초당 수십 건이라 지금은 여유가 있지만, 폭주 종목을
실험하려면 `Async` 발행이나 종목별 채널 + 단일 발행 고루틴으로 가야 한다. 결함이 아니라 설계 특성으로 기록한다.

### 4.7 (c) head-of-line — 파티션을 공유하는 종목은 핫 종목과 운명을 같이한다

핫 종목이 빠르기만 할 때(`hot`): 핫 종목 p50 11ms(오히려 낮다 — 배치가 빨리 찬다), 같은 파티션 종목 13.7ms, 다른 파티션 18ms. 영향 없음.
핫 종목 틱마다 2ms 를 먹을 때(`hot-slow`, 스레드 시간의 ~18%): 같은 파티션 17ms vs 다른 파티션 20ms. 여전히 영향 없음.
**10ms(~90%)**: 핫 종목 p50 5.8–6.8s, p99 12.8–14.3s, **같은 파티션 종목도 p50 5.9–6.8s, p99 12.8–14.3s 로 완전히 같이 밀렸고**, 다른 파티션 종목은
p50 17.5ms, p99 39–46ms 로 아무 일도 없었다. 20ms(~180%): 핫·같은 파티션 모두 p50 31–32s, p99 65–66s(40초 실행 뒤 90초 소진 대기 안에 못 끝남), 다른 파티션 p99 55–85ms.
3회 모두 같은 그림이다. 키=stockId 의 대가가 정확히 이것이다 — 파티션은 격리 단위이자 운명 공동체다. 지금 파이프라인은 틱당 비용이 일정해서(§4.4 CPU 0.3코어)
문제가 없지만, 종목별 비용이 큰 처리(예: 종목당 무거운 감지 규칙)를 리스너 스레드에 넣는 순간 그 종목의 파티션 이웃이 인질이 된다. 대응은 (1) 무거운 처리를
파티션 스레드에서 떼어 별도 큐로, (2) 핫 종목 전용 파티션(키 → 파티션 수동 매핑), (3) 종목별 처리 시간 상한 + 드롭.
