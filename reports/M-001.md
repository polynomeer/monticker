# M-001 — WebSocket push vs REST polling: 클라이언트 N 에서의 지연·서버 비용, Kafka 정지, 느린 소비자

> **페이퍼 트레이딩 규모의 개인 프로젝트다. 여기 숫자는 로컬 한 대(호스트 JVM/Go 프로세스 + k6 + Docker VM 안의 Kafka/Redis/Postgres)에서
> 잰 것이고 실제 운영 트래픽 검증이 아니다.** 조건당 3회 반복, 분위수는 p50/p95/p99, 평균은 쓰지 않는다.

- 실험 스크립트: [bench/experiments/](../bench/experiments/README.md) `m1-*.sh`, `m1-*.js`
- 원본 데이터: [`M-001/raw/`](M-001/) — k6 summary JSON, 프로세스 샘플, summary.tsv
- 실험일: 2026-09-17

## 0. 요청과 다른 전제 세 가지

요청(블로그 Track M · M1)은 이 저장소에 없는 것을 셋 전제했다. 실험은 실제 구조를 대상으로 했고 그 차이를 먼저 적는다.

1. **Netty broadcast-gateway 는 없다.** ADR-033 으로 제거됐다. WS 경로는 api 의 Spring STOMP(SimpleBroker) 하나다 —
   `market.ticks` → `MarketTickBroadcastConsumer`(파티션 수동 할당) → `PriceBroadcaster`(100ms conflation, ADR-038) → `/topic/stocks/{id}`.
2. **브로커는 Redpanda 가 아니라 Apache Kafka**(3.8.0, KRaft)다.
3. **Kafka → internal 자동 폴백은 없다.** `ingestion.source` 는 정적 설정이고, internal 경로(`MockPriceGenerator`)도 `market.ticks` 를 거친다
   (Stage 4 이후 모든 틱 경로가 Kafka 를 통과한다). 따라서 (b)는 "전환 시간"이 아니라 **Kafka 가 죽었다 살아날 때 클라이언트가 보는 침묵·유실·자동 재접속**을 쟀다.

## 1. 목적

- (a) WS push 와 REST polling(1s, 500ms)을 클라이언트 N ∈ {1,000, 5,000, 10,000} 에서 비교한다 — 사용자가 보는 tick→client 지연 p50/p95/p99,
  서버 CPU·메모리·스레드, msg/s 와 req/s.
- (b) Kafka 브로커를 강제 종료했다가 살릴 때: 클라이언트 침묵 시간, 그동안 만들어진 틱의 유실, 컨슈머·브로드캐스터의 자동 재접속, WS 연결 유지 여부.
- (c) 읽지 않는 WS 클라이언트(느린 소비자)가 있을 때 서버가 언제 끊는지, 다른 클라이언트가 영향을 받는지.

## 2. 방법

### 2.1 부하 모델

| 항목 | WS | polling |
|---|---|---|
| 틱 소스 | Go market-gateway, 202종목 × 1 tick/s (기본 간격) → Kafka → worker(Redis 최신가) / api(브로드캐스트) | 같음 |
| 클라이언트 | k6 VU N개, 각각 STOMP CONNECT 후 관심종목 **5개** `/topic/stocks/{id}` 구독, HOLD 60s 유지. 초당 ~200연결로 램프 | **도착률 모델**: 요청률 = N × 5 / 간격 (예: N=1,000·1s → 5,000 req/s). `constant-arrival-rate`, VU 풀 최대 3,000. 서버가 요청률을 못 받으면 `dropped_iterations` 가 쌓인다 |
| 지연 정의 | tick→client = 수신 시각 − 메시지 `timestamp`(틱 tradeTime). 같은 머신이라 시계 동일. **서버의 100ms conflation 포함** | staleness = 응답 수신 시각 − 응답 `tradeTime`. 폴링은 여기에 평균 간격/2 가 구조적으로 더해진다 |
| 서버 측 | api `process.cpu.usage`×10, `jvm.memory.used`, `jvm.threads.live` 5초 샘플; `ws_broadcast_messages_out_total` 증분 | 같음 + `http_reqs` |
| 우회 | — | `/api/**` IP당 300/분 레이트리밋을 `X-Bench: true` 로 우회(local 프로파일만 허용) |

api 는 `SPRING_PROFILES_ACTIVE=local`(show-sql·기동 재색인 끔), `-Xmx2g`, Tomcat 기본값(max-connections **8192**, max-threads 200). worker 는 기본 프로파일.

### 4.1 서버 비용: WS 는 폴링의 20분의 1 (D-M1-01: 폴링은 실시간 갱신 수단이 못 된다)

같은 클라이언트 수에서 api CPU 는 **WS 0.1–0.5 코어, 폴링 2.0–2.8 코어** — 10~20배다. 이유는 부하 모델에 다 들어 있다:
- WS 는 서버가 100ms conflation 후 종목당 최대 10 msg/s 를 민다. N=10,000 에서 89k msg/s 를 0.4 코어로 냈다.
- 폴링은 클라이언트가 관심종목 5개를 간격마다 당긴다. N=1,000·1s = 5,000 req/s 가 필요하고, **api 는 ~5,300–5,500 req/s 에서 천장을 쳤다**
  (N 을 5,000·10,000 으로 올려도, 간격을 500ms 로 줄여도 달성 req/s 는 그대로고 나머지는 drop). N=10,000·500ms 는 100,000 req/s 가 필요한데
  5.3k 만 나갔다 — 요청의 **95% 가 부족**했다. 즉 폴링으로 1만 명에게 0.5초 신선도를 주는 것은 이 서버로 불가능하다.
- 그런데 CPU 는 2.1 코어에서 더 안 올랐다 — 병목이 CPU 가 아니다. HTTP p99 가 천장에서 ~820ms 이고 k6 VU 3,000 이 전부 대기에 묶였다.
  매 요청이 `stockRepository.findById`(JPA, 캐시 없음) + Redis 최신가 조회를 하므로 커넥션 풀(Hikari 기본 10)·Tomcat 스레드 200 에서 직렬화된다.
  **폴링을 굳이 쓴다면** 최소한 종목 조회 캐시와 배치 엔드포인트(관심종목 N개를 한 번에)가 필요하지만, 그건 WS 가 이미 하는 일을 재발명하는 것이다.
- 신선도: WS tick→client p50 은 N=1,000 48ms → 10,000 243ms(전부 100ms conflation 포함). 폴링 staleness p50 은 간격과 무관하게 ~540ms
  (간격/2 + 처리) — **1초 폴링이든 WS 든, WS 가 항상 최신이고 더 싸다.** 결론은 이 저장소의 기존 결정(STOMP push, ADR-029·038)을 지지한다.

### 4.2 WS 확장의 두 벽 — 동시 연결 수(D-M1-02)와 연결당 힙

- **D-M1-02**: N=10,000 수정 전, 동시 연결이 정확히 Tomcat `max-connections` 기본값 **8,192** 에서 멈췄다(netstat ESTABLISHED 16,584 = 8,292 소켓).
  넘친 클라이언트는 조용히 accept 되지 못하고 k6 가 재시도했다(연결 실패 7k–14k). `server.tomcat.max-connections=20000` 으로 3회 모두 0 실패.
  이 값은 공짜가 아니다 — **연결당 api 힙 ~140KB**(N=1,000 730MB → 8,200 1,760–1,960MB, `-Xmx2g` 근처). 그래서 max-connections 는 반드시 `-Xmx` 와
  같이 정해야 하고(수정 후 `-Xmx3g`), 진짜 확장은 세로가 아니라 api pod 를 늘리는 것이다 — 그런데 그건 이미 ADR-038 이 풀어 둔 문제다(브로드캐스트 컨슈머가
  컨슈머 그룹 없이 전 파티션을 받으므로 pod 를 늘려도 모든 pod 가 모든 틱을 받는다). **이 실험은 "한 pod 의 상한이 ~8k 연결"임을 수치로 못 박는다.**

### 4.3 Kafka 정지: 자동 폴백은 없지만 자동 복구는 된다 — 대신 45초 침묵과 조용하지 않은 유실

§3.2, 3회 동일. 요청서의 "kafka→internal 전환 시간"은 이 저장소에 해당이 없다(§0-3). 실제로 일어난 일:
- **모든 시세가 45.7초 멈췄다**(관측 연결·k6 1,000연결 모두). 30초는 주입한 정지 시간, 나머지 15.3초는 `docker start` 후 브로커 healthy(+22–23s)까지와
  컨슈머 재연결이다. WS 연결 자체는 100% 유지됐다(k6 connect_ok 1.0) — api 는 살아 있고 틱만 안 왔다. 즉 사용자는 "연결은 됐는데 값이 안 변하는" 화면을 45초 본다.
- **유실 1,010건**, worker 의 seq gap 과 정확히 일치했고 게이트웨이의 `publish failed` 1,010 과도 일치했다(연결 거부 606·리셋 263·EOF 141).
  D-M2-01 을 고쳐 acks=all 이 됐으므로 이 유실은 **게이트웨이가 실패로 인지한** 유실이다 — 재시도 큐잉이나 로컬 버퍼가 없어 그대로 버려질 뿐, 조용하진 않다.
  개선하려면 게이트웨이에 디스크/메모리 버퍼 + 복구 후 재발행이 필요하다(현재 없음). 페이퍼 트레이딩·mock 틱에서는 다음 틱이 1초 뒤 오므로 감수 가능.
- 자동 복구는 확인됐다: worker `@KafkaListener` 와 api `MarketTickBroadcastConsumer`(10초 재시도 루프) 모두 재기동 없이 스스로 다시 붙었다. api 의
  `tick_broadcast_failed_total` 162–388 은 정지 순간 인플라이트였던 브로드캐스트가 `@Async` 리스너 풀에서 거부된 것(별개 관찰, 유실 경로 아님).

### 4.4 느린 소비자: 세션은 3초에 끊지만, 그것만으로는 전체가 20초 멈춘다 (D-M1-04)

§3.3·3.4(c). 읽지 않는 WS 연결 1개는 무해했다 — 3초 만에 버퍼 한도(512KB)에서 끊기고 정상 클라이언트 p99 161–179ms.
하지만 **느린 연결 25개**(기본 `clientOutboundChannel` 풀 크기 = 코어 수 10 보다 많다)는 **모든** 정상 클라이언트를 p95 14–17s, p99 17–19s 멈췄다(3회).
- 첫 시도(sendTimeLimit 10s→2s, 버퍼 512KB→256KB)는 **실패했다** — 세션은 여전히 3초에 끊겼지만 정상 p99 는 그대로 17–19s. 한도는 "나쁜 세션을 언제 끊나"를
  정할 뿐, 끊기 전까지 발행 스레드가 붙잡히는 것을 막지 못한다.
- 원인은 발행 스레드 풀이었다: `PriceBroadcaster` → `clientOutboundChannel`(기본 풀 10)이 느린 세션 send 로 다 차면 정상 클라이언트로 갈 메시지가 큐에 쌓인다.
  `app.ws.outbound-core-pool-size=50` 으로 늘리자 정상 p99 **191–196ms**, 최대 침묵 ~1.1s 로 떨어졌다(느린 세션은 여전히 3–4초에 끊김, `outboundChannel[pool size = 50]`
  · `Terminating … Buffer size … exceeds limit` 로그 확인). 완전한 격리는 아니지만(풀 > 느린 소비자 수를 전제) 20s → 0.2s 로 두 자릿수 개선이다.
  근본 격리는 send-per-session 비동기화 + 종목 conflation(이미 있음)의 조합이고, 풀 크기는 "느린 소비자 예산"으로 운영에서 잡아야 한다.

### 4.5 종합

이 저장소의 실시간 경로 설계(STOMP push + conflation, 브로드캐스트 컨슈머 pod 확장)는 폴링 대비 명확히 옳다(§4.1). 한 pod 의 현실적 상한은
**~8,000 동시 WS 연결**(max-connections·힙, §4.2)이고 그 위는 pod 를 늘리는 문제다. 운영 전 세 개의 기본값을 바꿔야 한다: `max-connections`(D-M1-02),
`clientOutboundChannel` 풀(D-M1-04), 그리고 이미 M-002 에서 고친 게이트웨이 acks(D-M2-01, §4.3 의 유실을 "조용한 유실"에서 "인지된 유실"로 바꾼 전제).
