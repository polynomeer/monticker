# 모의투자에 왜 리스크 한도가 필요한가

## 1. 직관적 반론: "가짜 돈인데 왜 막아야 하나"

모의투자는 잃어도 실제 손해가 없다. 그렇다면 주문 전 리스크 체크로 사용자를 막아서는 이유는 무엇인가 — monticker가 이 질문에 답하는 방식은 "모의투자의 목적이 무엇인가"를 다시 묻는 것이다.

모의투자가 단순히 "재미로 가짜 매매를 해보는 것"이라면 리스크 한도는 불필요한 마찰이다. 하지만 monticker의 모의투자는 **실제 투자 습관을 형성하는 연습장**이다. 연습 환경에서 무제한적인 행동이 허용되면, 사용자는 실제 투자에서도 똑같이 행동할 가능성이 높다 — 리스크 관리 없이 매매하는 습관 자체를 학습하게 되는 것이다.

## 2. 다섯 가지 한도가 가르치는 다섯 가지 원칙

| 한도 | 가르치는 원칙 |
|------|--------------|
| 일일 손실 한도 | "오늘 진 돈을 만회하려고 더 큰 베팅을 하지 마라" |
| 종목 집중도 한도 | "한 종목에 모든 것을 걸지 마라" |
| VaR 한도 | "포트폴리오 전체의 변동성을 인지하라" |
| 최대 보유 종목 수 | "너무 많은 종목을 동시에 추적하려 하지 마라" |
| 거래 빈도 한도 | "잦은 매매가 곧 좋은 전략은 아니다" |

각 한도는 임의의 숫자가 아니라, 개인 투자자가 실제로 자주 빠지는 행동 패턴에 대응한다. 예를 들어 "일일 손실 한도"는 손실 회피 편향(loss aversion)이 만드는 보복성 매매(revenge trading)를 구조적으로 차단한다 — 사용자가 의지로 참는 것이 아니라 시스템이 그 시점에 주문 자체를 막는다.

## 3. 사후 경고가 아니라 사전 차단인 이유

```
주문 전:  "이 주문을 실행하면 일일 손실 한도(3%)를 초과합니다" → 주문 거부
주문 후:  "오늘 손실이 한도를 초과했습니다" → 이미 늦음
```

대부분의 투자 앱은 손실이 발생한 *뒤에* 알림을 보낸다. 이는 정보 제공이지 행동 개입이 아니다. monticker는 주문이 체결되기 *전*에 차단함으로써, "알면서도 했다"가 아니라 "애초에 할 수 없었다"는 경험을 만든다. 이 차이는 습관 형성에서 결정적이다 — 사후 인지는 죄책감만 남기지만, 사전 차단은 그 행동 자체가 일어나지 않게 한다.

## 4. 투명성 — 차단의 이유를 항상 보여준다

```json
{
  "approved": false,
  "blockedBy": "일일 손실 한도 초과",
  "checks": [
    { "rule": "DAILY_LOSS", "passed": false, "detail": "오늘 손실 -3.4% / 한도 -3.0%" },
    { "rule": "CONCENTRATION", "passed": true, "detail": "삼성전자 비중 22.1% / 한도 30%" }
  ]
}
```

주문이 거부됐을 때 "거부됨"이라고만 말하면 사용자는 좌절하고 한도를 우회할 방법을 찾는다. 모든 규칙의 통과/실패 여부와 현재 수치를 함께 보여주는 이유는, 사용자가 **이 한도가 자신의 실제 상태를 정확히 반영한다**는 것을 납득해야 신뢰가 생기기 때문이다. "왜 막혔는지 모르겠다"는 경험이 반복되면 사용자는 시스템을 신뢰하지 않고, 신뢰하지 않는 안전장치는 무용하다.

## 5. 사용자가 한도를 직접 설정할 수 있게 한 이유

리스크 한도는 고정값이 아니라 사용자가 `/risk` 화면에서 직접 조정할 수 있다. 이는 "시스템이 정답을 안다"는 권위주의적 설계 대신, **사용자가 자신의 위험 허용도를 스스로 정의하고 그 약속을 시스템이 지켜준다**는 계약 관계로 리스크 관리를 재정의한다. 초보자는 보수적인 기본값(일일 손실 3%, 집중도 30%)을 그대로 두고, 경험이 쌓이면 스스로 한도를 조정하면서 "내가 감당할 수 있는 위험이 어느 정도인지"를 능동적으로 탐색하게 된다.

## 6. 체결 엔진과의 연결 — 왜 진짜 호가창이 필요한가

리스크 관리는 체결 가격이 현실적일 때만 의미가 있다. "현재가에 무조건 전량 체결"되는 환경에서는 슬리피지가 존재하지 않으므로, 대량 주문이 실제로 얼마나 불리한 평균가에 체결되는지 사용자가 체감할 수 없다. CLOB 기반 체결 엔진(`matching-engine-clob.md` 참고)이 부분 체결과 슬리피지를 시뮬레이션하는 것은 단순한 기술적 정교함이 아니라, "큰 주문은 시장에 충격을 준다"는 리스크 관리의 기초 교훈을 실제로 체감하게 하는 장치다.
