# ADR-067: 증권사 연동 해지 — 키 즉시 삭제, 결과가 열린 주문이 있으면 거부

## Status
Accepted

## Context

약관 제3조와 개인정보 처리방침은 "이용자는 언제든 연동을 해지할 수 있고, 해지 시 등록된 API 키는 즉시 파기된다"고 약속한다.
그런데 해지 경로가 없었다. 다른 계좌로 다시 연동하면 기존 계좌를 `is_active = false`로 돌릴 뿐, 암호화된 앱키·시크릿·토큰은
그대로 남았다([design-rollout-plan.md](../design-rollout-plan.md) P0-3).

키를 지우는 것 자체는 쉽다. 어려운 점은 **키가 아직 필요한 주문**이다.
- 결과 불명(`UNKNOWN`)·제출 대기(`PENDING_SUBMIT`) 주문은 대조 잡이 증권사에 물어 해소한다([ADR-056](056-brokerage-order-unknown-outcome.md)).
- 접수(`SUBMITTED`) 주문은 상태 동기화 잡이 60초마다 체결을 확인한다([ADR-061](061-brokerage-order-status-sync-and-single-settlement.md)).

두 잡 모두 그 주문 계좌의 자격증명을 쓴다. 키를 지운 뒤 체결되면 정산과 원장이 영영 맞지 않는다.

고려한 대안:
1. **즉시 삭제, 열린 주문은 운영자 수동 해소로 넘김.** 사용자 약속은 지킨다. 하지만 실거래 정산 불일치를 의도적으로 만든다.
2. **해지 예약.** 열린 주문이 닫히면 자동으로 삭제한다. 약속("즉시")과 다르고, 예약 상태와 그 처리 잡이 새로 생긴다.
3. **열린 주문이 있으면 거부, 없으면 즉시 삭제** — 채택.

## Decision

`DELETE /api/brokerage/account` (`BrokerageService.disconnect`), 한 트랜잭션:

1. 주문 준비와 **같은 사용자 advisory lock**(`ADVISORY_NS_ORDER`, userId)을 잡는다.
2. 활성 계좌를 찾는다. 없으면 409.
3. 아래 주문이 있으면 409로 거부한다(사유를 메시지로 준다). 동기화 잡과 같은 24시간 창을 쓴다. 그보다 오래된 접수 주문은 잡도 보지 않으므로 해지를 막지 않는다.
   - 결과가 열린 주문: `PENDING_SUBMIT`, `UNKNOWN`, 최근 24시간의 `SUBMITTED`
   - 발동 중인(`TRIGGERED`) 조건부 주문
4. 이 계좌의 `ACTIVE` 조건부 주문을 `CANCELLED`로 바꾼다. 남겨 두면 키 없는 계좌로 발동해 실패만 반복한다.
5. `access_token`·`app_key`·`app_secret`·`token_expires_at`·`provider_account_ref`·`auth_failed_at`을 NULL로 지운다.
   `is_active = false`, `disconnected_at = now()`(V57). 계좌 행은 주문·정산 기록의 기준이라 지우지 않는다.
6. 로그에는 userId·accountId·provider·취소 건수만 남긴다. 키 값은 남기지 않는다.

화면(`/brokerage/connect`)은 두 번 눌러야 실행한다. 거부 사유는 그대로 보여 준다. 재인증이 필요한(키가 무효인) 계좌도 해지할 수 있다.

증권사 쪽 토큰 폐기 API는 호출하지 않는다. 화면에서 "증권사 개발자센터에서 키를 폐기하라"고 권한다.

## Reasons

- 거부는 실거래 정산 정합성을 지킨다. 해지를 원하는 사용자는 미체결 주문을 취소하거나 1~2분(대조 주기) 기다리면 된다.
- 같은 advisory lock을 쓰므로 "열린 주문 없음 확인 → 키 삭제" 사이에 새 주문 의도가 끼어들 수 없다. 락을 기다리던 주문 준비는 해지 커밋 뒤 계좌를 찾지 못해 **증권사 호출 전에** 실패한다.
- 발동 확인을 취소보다 먼저 한다. 평가기는 이 락 없이 `ACTIVE → TRIGGERED`로 바꾼다. 그 사이 발동된 행은 위와 같이 주문 준비에서 실패하고, ADR-065 알림이 간다(증권사 호출 없음).
- 증권사 토큰 폐기는 증권사마다 다르다(KIS `/oauth2/revokeP`, Toss는 확인 필요). 실패해도 우리 쪽 삭제를 막으면 안 된다. 우리가 지우는 것만으로 약관 약속은 지켜진다.

## Consequences

- 확인 중인 주문이 있으면 사용자가 즉시 해지하지 못한다. 화면 메시지로 이유와 할 일을 알린다.
- 다른 계좌로 갈아탈 때(`connect`) 비활성화되는 기존 계좌는 여전히 키를 지우지 않는다. 그 계좌의 열린 주문을 대조하려면 키가 필요하기 때문이다. 열린 주문이 닫힌 뒤 비활성 계좌의 키를 지우는 정리 잡이 후속 과제다.
- `disconnected_at`이 생겼다. 비활성 사유(해지인지, 갈아타기인지)를 구분할 수 있다.

## Revisit When

- 증권사 토큰 폐기 API를 호출해야 할 규제·보안 요구가 생길 때.
- 비활성 계좌 키 정리 잡을 만들 때. 이 ADR의 "열린 주문" 정의를 그대로 재사용한다.
- 해지 거부가 실제 사용자 불만으로 반복될 때. 대안 2(해지 예약)를 다시 검토한다.
