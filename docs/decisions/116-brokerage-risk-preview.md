# ADR-116: 실전 주문 리스크 미리보기 — 증권사 잔고 기준, 제출은 막지 않음

## Status
Accepted

[ADR-092](092-risk-check-preview-without-audit.md)(모의 미리보기)를 실전으로 넓힌다. [ADR-025](025-real-brokerage-order-safety-gate.md)의
"실거래 판정에 모의 데이터를 쓰지 않는다"와 [ADR-069](069-risk-limit-changes-cooling-off.md)의 "실거래는 리스크 체크 끄기를 따르지 않는다"를 그대로 따른다.

## Context

실전 주문 화면(웹·앱)은 종목 집중도만 스스로 계산하고 일간 손실·VaR·보유 종목 수·시간당 주문 수·섹터 비중은 "서버 검증"으로만
보였다. `/api/risk/preview`는 모의계좌 상태로 판정하므로 실전에 쓸 수 없다. 사용자는 제출해야 422로 결과를 알았다.

판정에는 증권사 잔고가 필요해서 ADR-092와 달리 두 문제가 생긴다.

1. **증권사 호출 비용** — 입력마다 잔고를 부르면 증권사 호출 한도를 쓰고 느리다.
2. **진행 중 매수 갱신** — 게이트는 판정 전에 진행 중 매수 상태를 증권사에서 갱신한다(ADR-058). 이는 증권사 호출과 DB 쓰기다.

고려한 대안:

- **A. 화면이 잔고를 보내고 서버가 판정** — 호출은 줄지만 판정 입력을 클라이언트가 정한다.
- **B. 입력마다 증권사 조회** — 정확하지만 호출 비용이 크다.
- **C. 짧게 재사용하는 서버 잔고 + 갱신 생략** — 미리보기가 게이트보다 엄하게 나올 수 있다.
- **D. C에 더해 Redis 공유 캐시** — 인스턴스 간 호출은 줄지만 계좌 잔고가 프로세스 밖으로 나간다.

## Decision

**C.** `POST /api/brokerage/risk-preview` `{symbol, side, quantity, limitPrice?}` → `RiskCheckResult`.

```
BrokerageService.previewOrderRisk
  계좌 → 종목 → 잔고(10초 재사용, 인스턴스 메모리) → snapshotOf → RiskCheckerService.previewBrokerageOrder
```

- **같은 판정식**: 잔고 → 스냅샷 변환(`snapshotOf`)을 게이트와 공유하고, 규칙은 같은 `evaluateWithSnapshot`, 판정은 같은 `judge`다.
  단위 테스트가 같은 스냅샷에서 미리보기와 게이트의 결과가 같은지 확인한다.
- **부수 효과 없음**: 감사 행·`risk_check_total`·주문 행·진행 중 매수 갱신·advisory lock이 없다. 예외는 만료된 토큰 재발급이며 잔고 조회와 같은 동작이다.
- **게이트는 그대로**: 제출 시 항상 새 잔고로 다시 판정한다. 재사용 잔고를 쓰지 않는다.
- **제출을 막지 않음**: 미리보기가 실패로 판정해도 경고로만 보이고 버튼은 열어 둔다. 화면이 직접 계산한 집중도 차단은 그대로 둔다.
- **판정 범위**: 리스크 규칙만. 거래 중지·결과 불명 주문은 게이트가 별도로 막고 화면도 별도로 보여 준다.
- **실패 시**: 미리보기를 받지 못하면 그 규칙은 "서버 검증"으로 남는다. 통과로 보이지 않는다.
- **호출 제한**: 사용자당 60회/분, 키 `brokerage.risk-preview`. 화면은 400ms 디바운스.

## Reasons

- **왜 제출을 막지 않는가**: 체결됐지만 아직 갱신되지 않은 지정가 매수는 보유와 대기에 이중으로 잡힌다. 그 갱신은 제출 때 게이트에서만 일어난다.
  미리보기로 막으면 제출할 수 없어 갱신도 일어나지 않고, 잘못된 차단이 풀리지 않는다.
- **왜 재사용이 10초인가**: 입력 한 번 사이의 호출을 없애기에 충분하고, 묵은 값의 영향은 게이트가 잡는다. 사용자당 증권사 잔고 호출은 인스턴스마다 분당 6회 안쪽이다.
- **왜 인스턴스 메모리인가**: 인스턴스가 늘어도 호출이 조금 늘 뿐 판정이 틀어지지 않으므로 공유할 이유가 없고, 잔고를 Redis에 두지 않아도 된다.
- **왜 A가 아닌가**: 잔고를 서버가 가져오면 화면이 다른 값을 넣어 통과를 보이게 할 여지가 없다.

## Consequences

- 미리보기가 게이트보다 엄하거나 느슨할 수 있다. 잔고가 최대 10초 묵고, 진행 중 매수가 이중으로 잡힐 수 있다. "통과"는 보장이 아니므로 화면은 제출 때 다시 판정한다고 안내한다.
- 주문 직후 10초 동안은 미리보기 잔고가 주문 전 값일 수 있다.
- 인스턴스별 캐시라 동시 미스는 합치지 않는다. 증권사 호출 동안 락을 잡지 않기 위한 선택이다.

## Revisit When

- 증권사 체결 통지로 진행 중 매수가 실시간 갱신되면 — 이중 계산이 사라지므로 미리보기로 제출을 막을 수 있다.
- 증권사 호출 한도가 실제로 문제가 되면 — 공유 캐시를 다시 검토한다.
