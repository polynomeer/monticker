# ADR-082: 알림 설정을 Postgres에 두고 모든 발송 경로가 종류별로 적용한다

## Status
Accepted

[ADR-065](065-user-notifications-from-api.md)(api 사용자 알림 경로)의 Consequences "사용자 알림 설정을 보지 않는다 — 설정을 존중해야 하는
알림 종류가 생기면 명령에 분류를 더한다"를 이행한다. ADR-065의 결정(아웃박스 → `notify.user` → worker)은 그대로다.

## Context

`/settings/notifications` 화면은 설정을 저장했지만 **아무도 읽지 않았다.**

- 저장소가 Redis `notif:pref:{userId}`(만료 없음)뿐이었다. Redis는 캐시로 운영되므로 퇴출·재기동이면 설정이 사라지고 "전부 켜짐"으로 돌아간다.
- 발송 경로 셋 — worker `AlertDispatcher`(알림 규칙), `StockEventWriter`(관심종목 급등락·거래량 이벤트 푸시), `UserNotificationDispatcher`
  (`notify.user`) — 모두 설정을 보지 않았다. "가격 알림 끄기"를 눌러도 계속 왔다.
- 화면의 "전체 알림·거래량 급증·퀀트 시그널·체결·정산·전략 마켓 소식"은 필드조차 없었다(비활성 토글). 체결·정산과 퀀트 시그널은 보내는
  곳도 없었다.
- "전략 마켓 소식(프로모션)"은 광고성 정보다. 정보통신망법 §50은 수신 동의 없이 보내는 것을 금지한다 — 알림 설정만으로 보낼 수 없다.

고려한 대안:

- **저장소**: (1) Redis 유지 + worker가 같은 키를 읽기 — 가장 짧지만 퇴출되면 끈 사람에게 보낸다. (2) `users`에 JSON 컬럼 — 스키마 없이 늘릴 수
  있지만 기본값·검증이 코드 세 곳(api·worker·화면)에 흩어진다. (3) **전용 테이블, 명시적 불리언 컬럼** — 채택. 기본값이 DDL에 있다.
- **적용 위치**: (1) 발행자(api)가 설정을 보고 발행하지 않기 — 발행자가 여럿이고 worker 자체 경로(알림 규칙)는 api를 거치지 않는다.
  (2) **발송 직전(worker)에 한 정책 함수로** — 채택. 세 경로가 같은 규칙을 쓴다.

## Decision

1. **저장**: `notification_preferences`(V78, `user_id` PK). 행이 없으면 기본값. 옛 Redis 값은 행이 없을 때만 읽는다(api·worker 모두, 지연 이전).
   api가 저장하면 행을 upsert하고 옛 키를 지운다. 필드: 전체(`all_enabled`), 채널(푸시·이메일), 종류별 푸시·이메일 — 가격 알림·거래량 급증·
   뉴스·퀀트 시그널·체결·정산·전략 마켓 소식, 주간 리포트. 전략 마켓 소식만 기본 꺼짐.
2. **분류**: api `UserNotificationCommand`에 `category`(기본값 없음 — 새 알림은 끌 수 있는지부터 정한다). worker는 상위집합 enum
   (`PRICE_ALERT`·`VOLUME_SURGE` 추가)을 쓴다.
   - 끌 수 없음: `ORDER_OUTCOME`(결과 확인 중, ADR-056), `CONDITIONAL_ORDER`(발동 실패, ADR-065). 설정을 읽지도 않는다.
   - 끌 수 있음: `FILLS`·`QUANT_SIGNAL`·`STRATEGY_MARKET`(+ worker의 `PRICE_ALERT`·`VOLUME_SURGE`).
   - 와이어에 `category`가 없거나 모르는 값이면 **끌 수 없는 것으로** 본다 — 이 변경 전 메시지는 전부 끌 수 없는 종류였고, 새 종류 때문에
     주문 결과 알림을 버리지 않는다.
3. **정책**(`NotificationPolicy`, worker, 순수 함수): 끌 수 없음 → 푸시, 닿지 않으면 이메일. 끌 수 있음 → 전체가 꺼졌으면 없음; 광고성은 MARKETING
   최신 동의가 없으면 없음; 아니면 푸시 = 채널∧종류, 이메일 = 채널∧종류, 그리고 이메일을 고르지 않은 종류는 **푸시가 닿지 않을 때 이메일로 대체**
   (채널이 켜져 있을 때 — 예전 동작. 기기 없는 웹 사용자가 기본값에서 알림을 잃지 않게).
4. **경로**: `AlertDispatcher`는 규칙 종류로(거래량 급증 → `VOLUME_SURGE`, 그 밖 → `PRICE_ALERT`), 꺼졌으면 발동 이력을 `SUPPRESSED`로 남긴다.
   `StockEventWriter`는 사용자별로 걸러 푸시한다. `UserNotificationDispatcher`는 설정을 **중복 표시보다 먼저** 읽는다(읽기 실패 → 표시 없이 예외 →
   재시도). 설정 읽기 실패를 기본값으로 대체하지 않는다 — 끈 사람에게 보내게 된다.
5. **새 발행자**: 실거래 체결(`applyBrokerStatus`의 FILLED, 결과 불명 해소 경로는 해소 알림이 대신)·정산 완료(`settle`) → `FILLS`, 포워드 테스트 신호 →
   `QUANT_SIGNAL`(룰셋 주인). 모두 상태를 바꾸는 트랜잭션 안에서 발행한다(ADR-065).
6. **마케팅 동의**: 설정 화면에서 MARKETING만 다시 동의할 수 있게 했다(ADR-068 Note). worker는 최신 MARKETING 행의 `agreed`를 본다.

## Reasons

- 설정의 진실이 하나(Postgres)이고, 적용 규칙도 하나(정책 함수)다. 세 경로가 따로 판단하면 반드시 어긋난다.
- 끌 수 없는 알림을 분류로 명시해 "설정 때문에 이중 주문 경고를 못 받는" 경우가 구조적으로 없다.
- 광고성 정보는 설정과 동의를 **둘 다** 요구한다 — 동의 없는 발송이 설정 실수로 일어나지 않는다.

## Consequences

- 배포 순서: worker 먼저. 옛 worker의 `notify.user` 소비자는 모르는 필드(`category`)에서 역직렬화가 실패해 메시지를 DLT로 보낸다(이번에 소비자를
  관대하게 바꿨다 — 다음부터는 순서 무관). 광고성 종류를 새로 만들 때도 worker가 먼저 그 이름을 알아야 한다(모르면 끌 수 없는 것으로 보낸다).
- 알림마다 DB 조회가 하나(또는 둘) 는다. 캐시하지 않는다 — 끈 직후의 알림이 나가면 안 되고, 발송량이 그 비용을 문제 삼을 수준이 아니다.
  관심종목 이벤트 푸시는 사용자 묶음으로 한 번에 읽는다.
- 아직 보내는 곳이 없는 설정: 뉴스·공시(기존), 전략 마켓 소식, 구독한 전략의 신호, 모의 체결, 주간 리포트. 설정은 저장·적용되지만 발행자가 생겨야
  알림이 간다. 전략 마켓 소식 발행자는 발행 전 `ConsentService.isAgreed(MARKETING)`(문서 버전 포함)도 확인해야 한다 — worker는 최신 행의 동의
  여부만 본다.
- 방해 금지 시간(P2)은 아직 없다. 생기면 정책 함수에 시간 조건을 더하고, 끌 수 없는 종류는 그대로 통과시킨다.
- 옛 Redis 지연 이전 코드는 모든 사용자가 한 번씩 저장했거나 충분히 지난 뒤 지운다.

## Revisit When

- 인앱 알림함·발송 이력이 필요할 때(ADR-065와 같은 조건) — 억제된 알림도 이력에 남길지 함께 정한다.
- 알림 종류가 크게 늘어 컬럼 방식이 번거로워질 때 — (사용자, 종류, 채널) 행 모델로.
- 방해 금지 시간·카카오 알림톡(P2)을 도입할 때.
