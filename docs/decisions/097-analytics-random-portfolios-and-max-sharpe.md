# ADR-097: /analytics 분석 기간·무작위 포트폴리오 표본·샤프 비율 최대 지점

## Status
Accepted

## Context

[design-rollout-plan](../design-rollout-plan.md) P2 /analytics 행. 시안의 효율적 프론티어에는 회색 무작위 포트폴리오 점과
최대 샤프 점이 있다. 하지만 화면은 프론티어 11점만 그렸고, 분석 기간은 "보유 일봉 전체"로 고정이었다. 실제 코드는
최근 400일 중 일봉 253개를 읽었고, 종목마다 **마지막 N개를 잘라 길이만 맞췄다**. 그래서 휴장일이 다른 국내·해외 종목을
섞으면 서로 다른 날짜의 수익률이 같은 행에 놓였다.

정할 것이 네 가지였다.

1. **기간 입력.** 프리셋만 둘지, 직접 지정도 둘지. 상한은 어떻게 둘지.
2. **표본 분포.** 단체(simplex) 위 균등분포(Dirichlet(1)), 희소 표본을 섞는 Dirichlet(α<1), 꼭짓점 위주 표본을 검토했다.
3. **최대 샤프 계산.** 표본 최댓값만 쓰기, 볼록 재정식화 QP(`min wᵀΣw s.t. (μ−r_f)ᵀy = 1, y ≥ 0`, 외부 솔버 필요),
   표본 최댓값에서 출발하는 투영 경사상승을 검토했다.
4. **무위험 수익률.** 0 고정, 서버 설정, 요청 파라미터를 검토했다.

## Decision

**기간** — `period=3M|6M|1Y|2Y`(기본 `1Y`, KST 오늘까지) 또는 `period=CUSTOM&from&to`(KST 날짜, 양 끝 포함).
직접 지정은 60일 이상 3년 이하이고, `to`는 오늘 이후일 수 없다. 위반하면 400을 준다(`AnalysisPeriod`).
`/portfolio/optimize`·`/portfolio/frontier`·현재 보유 비교가 같은 기간을 쓴다.

**정렬** — 기간 안에서 **모든 종목이 함께 종가를 가진 날**만 남겨 일간 수익률을 만든다. 수익률이 30개 미만이면
400을 준다. 메시지에는 기간과 실제 개수를 넣는다. 응답의 `period`에는 실제 첫날·마지막날과 관측 수를 담는다.
DB 조회는 KST 경계를 Kotlin에서 계산해 `java.sql.Timestamp`로 바인딩한다.

**표본** — Dirichlet(1,…,1) 분포로 뽑는다. 각 성분을 −ln U로 뽑아 합으로 나누므로 롱 온리이고 합이 1이다.
`samples=100..2000`(기본 1000)이고, 범위를 벗어나면 400이다. 난수는 `SplittableRandom(20261008)`로 고정한다.
그래서 같은 입력이면 같은 점이 나온다. 응답에는 표본의 수익·위험·샤프만 담고 비중은 담지 않는다.

**최대 샤프** — 시작점은 표본 전부, 동일가중, 단일 종목 꼭짓점 n개, 프론티어 11점이다. 이 중 샤프가 가장 큰
점에서 출발해 투영 경사상승으로 다듬는다. 기울기는 `∇S = μ/σ − (wᵀμ − r_f)·Σw/σ³`이다. 매 단계 결과를 단체 위로
유클리드 투영하고(Duchi et al. 2008), 백트래킹 탐색으로 보폭을 정한다. 샤프가 **엄격히 오를 때만** 이동하고
최대 500회 반복한다. 그래서 결과는 언제나 롱 온리이고 합이 1이며, 어떤 표본의 샤프보다도 작지 않다. 계산은 연율화한
μ·Σ(×252)로 한다. 변동성이 0이라 샤프를 정의할 수 없으면 `maxSharpe=null`이다.

**무위험 수익률** — 서버 설정 `app.analytics.risk-free-rate`(환경변수 `ANALYTICS_RISK_FREE_RATE`)를 쓴다.
기본값은 0이고 허용 범위는 −0.05~0.2다. 범위를 벗어나면 기동에 실패한다. 응답의 `riskFreeRate`로 노출하고,
화면의 샤프 계산과 안내 문구도 이 값을 쓴다.

**표기** — 이 기능은 투자 권유가 아니라 분석 도구다. 화면은 이 점을 "샤프 비율 최대 지점 (과거 데이터 기준)"으로
부르고, "추천·권장·최적 투자" 같은 표현은 쓰지 않는다. 기존 면책 문구는 유지한다.

## Reasons

- **기간 입력.** 프리셋과 3년 상한이 있어서 종목 20개 × 일봉 약 760개로 DB 스캔과 공분산 계산의 상한이 정해진다.
  직접 지정은 백테스트 기간과 맞춰 보고 싶은 사용자를 위한 것이다.
- **표본 분포.** Dirichlet(1)은 "무작위 포트폴리오"의 표준적인 뜻(단체 위 균등)이다. 설명하기 쉽고 구현이
  세 줄이다. α<1 혼합은 종목이 많을 때 산점도를 더 넓게 펼치지만, 분포를 하나 더 설명해야 한다.
- **최대 샤프 계산.** 표본 최댓값만 쓰면 종목이 늘수록 실제 최대에서 멀어진다(차원의 저주). 볼록 QP는 정확하지만
  솔버 의존성이 생기고, 모든 μ_i ≤ r_f인 경우를 따로 처리해야 한다. 경사상승은 의존성이 없다. 또 "표본보다 나쁘지
  않다"는 보장을 테스트로 고정할 수 있다. 상관이 없는 내부 해에서는 해석해(w ∝ Σ⁻¹(μ−r_f))와 1e-4 이내로 맞는다.
- **고정 시드.** 다시 실행할 때마다 점이 흔들리면 사용자는 결과가 바뀐 이유가 데이터인지 난수인지 구분할 수 없다.
  테스트도 결정적이 된다.
- **무위험 수익률.** 국내·해외 종목을 섞으므로 특정 통화 금리를 기본값으로 박지 않는다. 요청 파라미터로 받으면
  사용자가 샤프를 임의로 부풀려 볼 수 있어서 서버 설정으로 둔다.

## Consequences

- `/portfolio/frontier`의 응답이 배열에서 객체(`frontier`·`samples`·`maxSharpe`·`period`·`riskFreeRate`·`seed`·`method`)로
  바뀌었다. 클라이언트는 웹 /analytics 하나뿐이라 함께 바꿨다. 입력 오류와 데이터 부족은 빈 배열 대신 400이다.
- 날짜 교집합을 쓰므로 상장일이 늦거나 거래가 드문 종목이 하나 있으면 전체 관측 수가 줄어든다. 메시지는 이 경우
  "기간을 늘리거나 종목을 바꿔 보라"고 안내한다.
- 경사상승은 국소 방법이다. 초과수익이 양수인 영역에서 샤프는 준오목(quasi-concave)이라 이론상 전역 최대에 수렴한다. 하지만 모든 종목의
  초과수익이 음수면 이 성질이 없다. 또
  수치적으로는 백트래킹 하한(1e-12)과 반복 상한(500)에서 멈출 수 있다. 화면에는 "과거 데이터 기준"이라고만 표시한다.
- 프론티어 11점은 기존 페널티 경사하강 근사를 그대로 쓴다. 그래서 무작위 표본 일부가 프론티어 선보다 약간 위에
  찍힐 수 있다. 근사 오차다.
- `/portfolio/optimize`의 캐시 키에 기간(from·to)이 들어갔다. 기존 캐시 항목은 다시 맞지 않고 30분 TTL로 사라진다.
- 표본 2000개 × 종목 20개 계산은 수 ms 수준이다. 요청마다 `portfolio_optimizations`에 한 행을 남기는 기존 동작은
  유지한다. 저장하는 `weights_json`은 이제 샤프 최대 지점의 비중이다.

## Revisit When

- 종목 상한(20)을 크게 올리거나 공매도·비중 상한 같은 제약을 넣을 때. 이때는 볼록 QP 솔버가 낫다.
- 프론티어 근사 오차가 눈에 띄어 사용자 문의가 생길 때. 프론티어도 같은 투영 기법이나 QP로 바꾼다.
- 통화별 무위험 수익률이 필요해질 때. 예를 들어 원화 환산 수익률로 통일하는 경우다.
- 분석 결과를 리밸런싱 초안으로 넘기는 흐름에 샤프 최대 지점 비중을 추가할 때. 이때는 표기와 면책 문구를 다시 검토한다.
