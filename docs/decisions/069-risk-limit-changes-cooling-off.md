# ADR-069: 리스크 한도 변경 — 완화 24시간 쿨링오프, 리스크 체크 끄기의 범위, 섹터 집중도 한도

## Status
Accepted

## Context

리스크 한도(`risk_limits`)는 모의투자 게이트와 실거래 게이트([ADR-025](025-real-brokerage-order-safety-gate.md))가 함께 쓴다.
그런데 수정 경로(`PUT /api/risk/limits`)는 아무 검증 없이 값을 바로 덮어썼다. 음수·0도 들어갔다. 손실을 본 직후 한도를 풀고 곧바로 더 큰
주문을 내는 데 아무 마찰이 없었다. 한도의 존재 이유를 가장 필요한 순간에 스스로 없앨 수 있었다.

`is_active` 컬럼은 처음부터 있었지만 판정이 읽지 않았다. 화면의 "리스크 체크 활성화" 토글도 실제로는 아무것도 바꾸지 못했다.
리스크 화면에는 섹터 비중이 계산돼 보였지만 섹터 한도 규칙은 없었다.

이번에 세 가지를 함께 정한다. 셋 다 "한도를 어떻게 바꾸는가"의 문제이기 때문이다.

고려한 대안:
1. **즉시 적용 유지 + 검증만 추가** — 값 오류는 막는다. 하지만 감정적 완화는 그대로다.
2. **모든 변경을 24시간 뒤 적용** — 강화도 늦어진다. 위험을 줄이려는 사용자를 하루 동안 위험에 둔다.
3. **강화는 즉시, 완화만 24시간 뒤** — 채택. 증권사·코인 거래소의 한도 완화 대기와 같은 비대칭이다.

리스크 체크 끄기의 범위:
- (a) 모의·실거래 모두 끔 — 실거래 게이트를 사용자가 끌 수 있게 된다. 실제 돈이 걸린 경로의 안전장치를 사용자 설정 하나로 없애는 것은 ADR-025의 전제에 어긋난다.
- (b) **모의투자만 끔, 끄기는 완화로 보고 24시간 뒤 적용** — 채택.
- (c) 끄기 자체를 없앰 — 모의투자에서 한도 없이 연습하고 싶은 사용자의 요구를 막는다. 모의투자 주문은 컨트롤러 레이트 리밋이 따로 있다.

## Decision

### 쿨링오프
- **완화**는 한도를 올리기, 섹터 한도 해제, 리스크 체크 끄기다. 판정은 `RiskLimitField.looseness`가 한다. 값이 클수록 느슨하다. 섹터 한도 해제(null)는 무한대로, 끔(0)은 켬(1)보다 느슨한 것으로 본다.
- 완화는 `risk_limit_pending_changes (user_id, field)`에 항목당 하나 둔다. `effective_at = 요청 + 24h`.
  - 더 느슨한 값으로 다시 요청하면 시계가 다시 24시간부터 돈다.
  - 덜 느슨한 값으로 줄이면 기존 `effective_at`을 유지한다. 더 느슨한 값이 그 시각에 적용될 예정이었으므로 안전하다.
  - 현재 값과 같은 값을 보내면 그 항목의 대기 변경을 취소한다. 화면의 "취소"가 이 경로다.
- **강화**는 `risk_limits`에 바로 쓰고, 같은 항목의 대기 변경을 지운다.
- 쓰기는 `RiskLimitService` 한 곳에서만 한다. `risk_limits` 행 잠금(`findForUpdate`)으로 같은 사용자의 동시 수정을 직렬화한다.
  행 생성은 `INSERT … ON CONFLICT DO NOTHING`으로 해서 동시 생성 경합을 흡수한다.
  `RiskLimitRepository`는 더 이상 모듈 밖에 공개하지 않는다(NamedInterface 제거).
- 판정(`RiskCheckerService`, 근접 경고)은 `effective(userId)`를 쓴다. 저장된 한도에 적용 시각이 지난 대기 변경을 메모리에서
  얹은 사본이다. 판정 경로에서는 쓰지 않고 잠그지도 않는다. DB 반영(승격)은 조회(`view`)·수정 때 잠금 아래에서 한다.
  승격 도중에 읽어도 유효 한도는 승격 전후 값 중 하나이거나 더 엄격하다(READ COMMITTED에서 base 갱신 전 + pending 삭제 후를 보면 옛 base = 더 엄격).
- 값 검증은 서버가 한다. % 항목은 0.01~100(소수 둘째 자리), 개수 항목은 1~1000 정수다. 하나라도 틀리면 아무것도 바꾸지 않는다(400).
- 응답 `RiskLimitsDto`는 지금 유효한 값과 `pendingChanges[] {field, value, requestedAt, effectiveAt}`, `coolingOffHours`를 준다.

### 리스크 체크 활성화(`isActive`)
- `PUT /api/risk/limits`가 `isActive`를 받는다. 끄기는 24시간 뒤, 켜기는 즉시 적용된다.
- 꺼져 있으면 **모의투자** 판정(`check`)은 한도 규칙을 평가하지 않는다. 다만 `QuantityRule`(수량 ≤ 0)은 남긴다. 사용자 선호가 아니라 입력 검증이기 때문이다.
  판정과 감사 로그는 그대로 남고 `RiskChecksDisabled`(통과) 항목이 붙는다.
- **실거래** 판정(`checkBrokerageOrder`)은 `isActive`를 보지 않는다. 한도 값은 같은 유효 한도를 쓴다. 따라서 실거래 한도의 완화도 24시간 뒤에 적용된다.
- 근접 경고([ADR-070](070-risk-limit-near-warnings.md))는 꺼진 사용자를 건너뛴다.

### 섹터 집중도 한도(`SectorConcentrationRule`)
- `risk_limits.sector_concentration_limit_pct` NULL = 미설정이다. 미설정이면 규칙을 평가하지 않는다. 기존 사용자의 동작은 바뀌지 않는다.
- 매수에만 건다. 값은 (주문 종목 섹터의 보유 + 진행 중 매수([ADR-058](058-risk-gate-in-flight-exposure.md)) + 이번 주문) 평가액 / 총자산이다.
  분모는 단일 종목 집중도와 같다. 실거래는 증권사 총평가액, 모의투자는 현금 + 보유 평가액이다.
- 섹터는 `stocks.sector`를 쓴다. 섹터가 비어 있는 종목은 어떤 섹터 합에도 들어가지 않으므로 이 규칙의 대상이 아니다(통과, 사유에 "미분류" 명시).
- 추정가, 같은 섹터 보유의 가격, 총자산 중 하나라도 모르면 막는다(V-H3과 같은 원칙).
- 설정은 강화(즉시), 해제와 한도 올리기는 완화(24시간 뒤)다. API에서 해제는 `clearSectorConcentrationLimit: true`로 표현한다. JSON null은 "변경 없음"이기 때문이다.

## Reasons

- 비대칭 지연은 사용자 자율을 크게 해치지 않는다. 위험을 줄이는 쪽은 즉시 되고, 늘리는 쪽만 하루를 기다린다. 대신 손실 직후의 충동적 완화를 막는다.
- 대기 변경을 별도 테이블로 두면 `risk_limits` 스키마와 판정 코드가 그대로다. 판정은 "저장값 + 기한 지난 대기분" 사본만 받는다.
  읽기 경로에 쓰기가 섞이지 않아 주문 경로에 행 잠금 경합이 생기지 않는다.
- 실거래 게이트를 끌 수 없게 하는 것이 가장 단순하고 안전한 규칙이다. 모의투자 연습의 자유는 남는다.

## Consequences

- 신규 사용자도 기본값보다 느슨한 한도를 원하면 24시간을 기다린다. 기본값은 기존과 같다(일손실 3%, 집중도 30%, VaR 5%, 10종목, 시간당 5회).
- 판정마다 대기 변경 조회가 한 번 늘었다(PK 앞부분 조회라 가볍다).
- 섹터 분류 품질이 규칙 품질이다. `stocks.sector`가 비어 있는 종목이 많으면 한도가 덜 걸린다. 분류 출처를 바꾸면 기존 보유의 합산도 바뀐다.
- 화면 문구가 바뀌었다. 예전 문구 "실제 투자에는 적용되지 않습니다"는 사실이 아니었다. 실거래 게이트는 ADR-025 이후 같은 한도를 써 왔다.

## Revisit When

- 한도 초과 시 "경고 후 진행" 모드(severity WARNING)를 도입할 때. 경고 모드로 바꾸는 것도 완화로 다뤄야 한다.
- 실거래와 모의투자 한도를 분리하자는 요구가 생길 때. 지금은 한 벌이다.
- 쿨링오프 시간을 사용자·상품별로 달리해야 할 때(규제·약관 요구 포함).
- 섹터 분류 체계(GICS·KRX 업종)를 정식으로 들일 때.
