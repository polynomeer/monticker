# ADR-096: 모의 지정가 대기 순번은 "스위퍼 처리 순서"로 정의하고, 남의 주문은 이어진 구간 합계로만 보인다 · 영수증 예약 잠금 단계

## Status
Accepted

## Context

design-rollout-plan §3의 P2 두 줄을 채운다.

1. **/matching "가격별 주문 대기열 조각, 내 주문 · 대기 N번째"** — 오더북 행에 시장 호가 잔량 막대 하나와 "내 주문 · N주 대기"만
   있었다. 호가 API(`/api/stocks/{id}/orderbook`)는 시장 호가이고 모의 주문은 들어 있지 않다.
2. **/wallet 영수증 "예약금 잠금" 단계** — 영수증은 접수 → 체결 → 정산 3단계(모두 체결 시각)였다. 지정가는 접수 때 현금을
   잠그지만(ADR-074) 그 시각은 어디에도 없었다.

### 엔진이 실제로 체결하는 순서 (코드 확인)

"순번"을 정의하려면 체결 순서가 정말 가격·시간 우선인지부터 봐야 했다. 화면 상단 통계는 "엔진: 가격·시간 우선"이라고 적고 있었다.

- 체결 근거는 힙 호가창이 아니라 DB다(ADR-048·074). 미체결 LIMIT은 `LimitOrderSweeper`(3초)가 `orders × 최신 candles_1m 종가`로
  판정해 `LimitOrderFiller`가 한 건씩(`FOR UPDATE SKIP LOCKED`) 체결한다.
- 후보 정렬은 `ORDER BY o.created_at` — **가격 우선이 아니고 종목·가격을 가리지 않는 접수 순**이었다. 동률(같은 `created_at`)은
  순서가 정해지지 않았다.
- 체결은 **유동성 제한이 없다**: 교차한 주문은 모두 그 순간의 종가로 **전량** 체결된다(ADR-074 Consequences). 앞 주문이 잔량을
  "먹어서" 뒤 주문이 못 받는 일이 없다. 그래서 순번이 결과를 바꾸는 경우는 후보가 배치(기본 200)를 넘어 다음 주기로 밀릴 때뿐이다.
- 제출 순간 교차한 새 지정가는 사가가 **즉시** 체결한다. 같은 가격에 먼저 걸린 주문은 다음 스위프(최대 3초)에 체결되므로,
  늦게 낸 주문이 먼저 체결될 수 있다 — 엄격한 FIFO가 아니다.
- 엔진은 부분 체결을 만들지 않는다(전량 체결). `PARTIALLY_FILLED`·체결 여러 건은 스키마가 허용하고 화면이 다룰 뿐이다.

### 후보

- 순번 정의
  - **(a) 가격·시간 우선 큐 순번** — 실제 엔진과 다르다. 화면이 거짓말을 한다. 기각.
  - **(b) 스위퍼 처리 순서의 같은 가격·방향 안 위치** — 사실 그대로다. 의미가 약하다는 것을 함께 말해야 한다.
- 남의 주문 노출
  - **(c) 주문별 조각(익명)** — 거래소 L3처럼 주문마다 수량을 보인다. 개별 주문 크기·접수 순서가 다른 사용자의 행동을 드러낸다.
  - **(d) 가격별 합계만** — "조각"이 없다. 내 앞뒤가 보이지 않는다.
  - **(e) 내 주문을 경계로 이어진 남의 구간을 합친 조각** — 내 앞 몇 건·몇 주, 뒤 몇 건·몇 주만 보인다.
- 예약 시각
  - `order_sagas.started_at`을 쓴다 — 검증 전 시각이고 사가 행은 주문과 수명이 다르다.
  - **`orders.reserved_at`을 추가해 잠금이 성공한 순간 기록**한다.

## Decision

**(b) + (e) + `orders.reserved_at`.**

### 1. 대기열 API — `GET /api/matching/queue?stockId=` (인증 필수, 읽기 전용)

```
OrderQueueService.QUEUE_SQL (한 문장 = 한 스냅샷)
  q: 미체결 LIMIT(PENDING·PARTIALLY_FILLED, 잔량 > 0)
     row_number() OVER (PARTITION BY side, limit_price ORDER BY created_at, id)  ← 순번
  r: 내 주문 여부로 연속 구간(gaps-and-islands) 번호
  GROUP BY side, price, mine, (mine ? id : 구간)  → 조각: 건수·잔량 합·시작 순번(내 조각만 orderId)
→ { bids(높은 가격부터), asks(낮은 가격부터) : [{price, orderCount, quantity, slices}], mine: [{orderId, position, aheadCount, aheadQuantity, …}] }
```

- **순번 = 스위퍼 처리 순서 `(created_at, id)`의 같은 가격·방향 안 위치.** 스위퍼 정렬에 `, o.id`를 더해 동률을 끊었다 —
  대기열 SQL과 스위퍼가 같은 순서를 쓴다(통합 테스트가 두 SQL의 결과를 비교한다).
- **화면은 순번의 한계를 그대로 말한다**: "모의 체결은 잔량 제한이 없어, 시세가 지정가에 닿으면 순번과 관계없이 함께
  체결됩니다." 상단 통계의 "엔진: 가격·시간 우선"은 "접수 순 처리"로 바꿨다.
- 방향마다 최우선부터 20개 가격만 보이고, 내 주문이 걸린 가격은 그 밖이어도 포함한다. `mine`은 상한이 없다.
- 시장 호가 행과 가격이 같을 때 그 행에 조각을 그리고, 호가 범위 밖의 내 주문은 표 아래 목록으로 보인다.

### 2. 프라이버시 — 남의 주문에서 나가는 것

| 나가는 것 | 나가지 않는 것 |
|---|---|
| 가격별 건수·잔량 합(일반 L2 호가와 같은 수준) | 다른 사용자 id·주문 id |
| 내 주문 사이에 낀 남의 **연속 구간**의 건수·잔량 합 | 남의 주문별 수량 목록·접수 시각·출처 |
| | 다른 사용자가 보는 화면에서 내 주문의 존재 구분(내 주문도 그들에겐 남의 구간에 합쳐진다) |

남의 개별 주문 행은 DB 밖으로 나오지 않는다(집계까지 SQL 안에서 끝난다). 구간이 1건이면 그 1건의 잔량이 보이는데, 이는 가격에
주문이 1건일 때 L2 합계가 이미 드러내는 것과 같은 정보이고 누구의 주문인지·언제 냈는지는 없다 — 받아들인다.
조회는 `stockId`만 받고 사용자 소유 자원이 아니므로 404 패리티 대상이 아니다(없는 종목은 빈 대기열).

### 3. 영수증 예약 잠금 단계 — V93 `orders.reserved_at`

- 사가(`OrderSagaOrchestrator`)가 **BUY는 현금 예약 UPDATE가 성공한 직후, SELL은 포지션 `FOR UPDATE` 아래 매도 가능 수량 판정을
  통과한 직후** 시각을 잡아 주문 INSERT에 넣는다. 같은 사가 트랜잭션이라 값이 있으면 잠금도 있었다(롤백되면 둘 다 없다).
- 잠근 금액은 저장하지 않는다 — 지정가 BUY는 정의상 `limit_price × quantity`(ADR-074).
- `GET /api/paper/trades/{id}/receipt`에 `order`(주문 진행 기록)를 더했다: 접수 시각(`submitted_at`, 없으면 `created_at`),
  `reservedAt`, `reservedAmount`(지정가 BUY)·`reservedQty`(지정가 SELL), 주문의 모든 체결(이 영수증의 체결 표시), 취소 시각
  (`CANCELLED`면 `updated_at`)과 엔진 취소 사유. `paper_trades → fills → orders` 한 문장이며 거래·주문 모두 호출자 소유여야
  한다. 소유 확인(404 패리티)은 그 전에 끝난다 — 남의 거래면 이 조회를 부르지도 않는다.
- 화면: **지정가는 접수 → 예약금 잠금(SELL은 "매도 수량 잠금") → 체결(부분 체결·잔량 취소 표시) → 정산**, 시장가와 ADR-047 이전
  거래(`fill_id` 없음)는 예전 3단계. V93 이전 지정가는 잠금 단계를 "시각 기록 없음"으로 보인다(잠금 자체는 ADR-074 이후 항상 있었다).
  정산은 그 거래(체결 한 건)의 T+2 기록이다 — 부분 체결이면 체결마다 따로 정산된다.

## Reasons

- **(b)**: 화면의 숫자는 엔진이 실제로 하는 일과 같아야 한다. 가격·시간 우선 큐 순번을 보이면 "3번째니까 앞 두 건이 체결돼야
  내 차례"라고 읽히는데, 실제로는 셋 다 같은 순간에 체결된다.
- **(e)**: "내 앞에 몇 건"이라는 질문에 답하면서 남의 주문 크기·순서를 주문 단위로 풀지 않는다. (c)는 이득(남의 개별 크기)이
  모의투자 사용자에게 필요하지 않다.
- **한 문장 스냅샷**: 순번·조각·합계를 같은 스냅샷에서 계산해 동시 접수·취소 중에도 순번이 1부터 빈틈없이 이어지고 합계가 맞는다
  (READ COMMITTED에서도 한 문장은 한 스냅샷을 본다).
- **`reserved_at`**: 잠금 성공 시각을 그 트랜잭션 안에서 남기는 것이 "예약금 잠금"을 사실로 보이는 유일한 방법이다.

## Consequences

- 대기열 조회 비용은 종목의 미체결 LIMIT 수에 비례한다(`idx_orders_stock_status`). 3초 폴링이라 미체결이 수만 건이 되면 부담이다.
- 순번은 정보성이다. 단일 라이터 매칭(scale-out-plan §6.8)으로 유동성이 생기면 순번의 의미가 바뀐다 — 그때 이 ADR을 대체한다.
- 시장 호가 가격과 모의 지정가가 다르면(호가 단위 밖 지정가 등) 조각은 표 아래 목록으로만 보인다.
- 취소 시각은 주문 행의 마지막 변경 시각이다. 취소 뒤 행을 다시 바꾸는 경로가 생기면 `cancelled_at`이 필요하다.
- 체결 없이 취소된 주문은 거래가 없어 영수증도 없다(미체결 목록·주문 내역에서만 보인다).

## Revisit When

- 모의 체결에 유동성 모형(잔량 소진·부분 체결)이 생기거나 호가창이 체결 근거가 될 때(scale-out-plan §6.8) — 순번이 결과를 바꾸게 된다.
- 사용자 수가 늘어 1건 구간의 잔량 노출도 문제가 될 때 — 구간 건수가 k 미만이면 잔량을 숨기는 k-익명 규칙을 검토한다.
- 체결 없이 취소된 지정가에도 영수증이 필요해질 때 — 주문 단위 영수증 API.
