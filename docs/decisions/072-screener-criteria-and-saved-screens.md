# ADR-072: 스크리너 조건(섹터·범위·오늘 이벤트)·저장 스크린·장중 미니 시계열

## Status
Accepted

## Context

터미널 디자인 시안(ADR-066)의 /screener에는 섹터 칩, 등락률·거래량 배수 범위 슬라이더, "오늘 발생한 이벤트" 체크박스(뉴스·공시 동반, 퀀트 시그널, 감성 급변), 조건 저장과 저장한 스크린 탭, 결과 열의 거래량 배수·오늘 스파크라인·이벤트가 있다. 기존 `/api/screener`는 시장·시가총액 구간·정렬만 받았고, 나머지는 화면에 비활성으로만 있었다(design-rollout-plan §2). /watchlist의 "오늘"·"거래량 배수" 열도 같은 데이터가 필요하다.

정해야 했던 것:

1. **거래량 배수의 정의.** 시안 라벨은 "5분 평균 대비"였다. 후보:
   - (a) 최근 5분 거래량 ÷ 그 전 N분 평균 — 분봉 기준. 장 시작 직후·점심시간에 크게 흔들리고, 장이 닫히면 의미가 없다.
   - (b) 당일 누적 거래량 ÷ 직전 20거래일 평균 일 거래량 — 일봉 기준. 장 초반에는 1보다 작게 나오지만 정의가 단순하고 장 마감 뒤에도 의미가 있다.
   - (c) (b)를 장 경과 시간으로 보정 — 국내·해외 장 시간과 휴장일을 알아야 하는데 휴장일 캘린더가 없다.
2. **이벤트 체크박스를 여러 개 골랐을 때** AND인가 OR인가.
3. **"퀀트 시그널 발생" 필터가 누구의 신호를 보는가.** `quant_signals` 전체를 보면 남의 비공개 룰셋이나 구독하지 않은 유료 전략이 오늘 어떤 종목에 신호를 냈는지가 새어 나간다 — ADR-035가 막은 것과 같은 종류의 누출이다.
4. **조건 저장 위치와 형태.**
5. **스파크라인 데이터.** 종목마다 `/candles?interval=1m`을 부르면 행 수만큼 요청이 나간다.

## Decision

1. **조건 타입 하나 — `ScreenerCriteria`.** 쿼리 파라미터와 저장 스크린이 같은 타입, 같은 `normalized()` 검증을 쓴다. market·marketCapTier·sort는 화이트리스트, 등락률은 -100~1000%, 거래량 배수는 0~1000, 섹터는 최대 20개·100자. SQL에는 화이트리스트를 통과한 상수만 문자열로 들어가고 나머지는 모두 바인딩한다. 저장 경로로 검증을 우회할 수 없다.
2. **거래량 배수 = 최신 일봉 거래량 ÷ 직전 20거래일 평균 (b).** candles_1d의 최신 행은 장중 실시간 upsert되는 오늘 행이다(ADR-021). 화면 라벨을 "20일 평균 대비"로 바꿔 정의를 그대로 드러낸다. 홈 이벤트 피드의 "거래량 배수"는 이벤트 시점 지표라 정의가 다르다(직후 5분 ÷ 직전 60분, 1분봉) — 두 화면의 툴팁에 각각 정의를 적는다.
3. **계산 비용**: 거래량 배수용 일봉 LATERAL(최신 1행 + 20행 평균)은 **필터(`minVolMult`)나 정렬(`volmult`)에 쓰일 때만** 전 종목 쿼리에 붙인다. 표시용 배수와 오늘 이벤트는 페이지에 오른 종목(≤50)에 대해서만 별도 쿼리로 붙인다(`findDayContext`). 계산 컬럼 조건이 없으면 count도 LATERAL 없이 센다.
4. **오늘 이벤트 필터는 AND**(모두 만족)다. 체크할수록 결과가 좁아지는 다른 필터와 같은 방향이다. "오늘" = KST 자정부터.
5. **퀀트 시그널 필터는 로그인 필수, ADR-035 접근 규칙 그대로.** screener가 `quant::api`의 `QuantSignalFeedService.stockIdsWithSignalsSince(userId, todayStart)`를 부른다 — 내 룰셋 + 구독한 마켓 전략의 신호만. 홈 "퀀트 시그널" 패널(`GET /api/quant/signals/feed`)도 같은 함수로 접근 가능 룰셋을 고른다. 이 조건이 있을 때만 **캐시 키에 userId를 넣는다**(5초 스크리너 캐시로 다른 사용자에게 결과가 새지 않게). 비로그인이면 401.
6. **저장 스크린은 `saved_screens`(V63) — 사용자·이름·`criteria` JSONB.** 사용자당 20개, 이름 1~40자·사용자 안에서 유일. 개수 확인과 INSERT 사이 경쟁은 사용자별 `pg_advisory_xact_lock(72001, userId)`로 직렬화한다. 모든 조회·수정·삭제는 `user_id` 조건을 함께 걸어 남의 행은 404로 보인다. 읽을 때 다시 검증해, 규칙이 바뀌어 무효가 된 행은 목록에서 빠진다. `GET /api/screener/saved/{id}/run`이 저장 조건으로 실행한다(웹은 탭을 고르면 조건을 필터에 불러와 같은 결과를 보여준다).
7. **장중 미니 시계열 일괄 API — `GET /api/market/intraday?ids=`.** 최대 50종목, 종목별 마지막 1분봉부터 11시간 안의 1분봉을 10분 버킷 마지막 종가로 줄인다(종목당 최대 66점). Redis 캐시 30초. 무한 스크롤 목록은 불러온 순서대로 50개씩 나눠 요청한다.

## Reasons

- **(b)를 고른 이유**: 장이 닫혀 있어도, 장 초반에도 같은 정의로 비교 가능하고 계산이 일봉 21행으로 끝난다. (a)는 슬라이더로 걸러 내기엔 너무 흔들리고, (c)는 휴장일·세션 데이터 없이 만들면 틀린 보정이 들어간다. 장 초반에 값이 작게 나오는 한계는 라벨과 툴팁으로 드러낸다.
- **조건 타입을 하나로 둔 이유**: 쿼리 파라미터와 저장 경로의 검증이 갈라지면, 저장 스크린이 검증 안 된 값을 SQL로 들고 들어오는 구멍이 생긴다.
- **퀀트 필터를 quant 모듈 함수로 위임한 이유**: 접근 규칙을 screener가 SQL로 다시 쓰면 ADR-035 규칙이 바뀔 때 한쪽만 고쳐진다. 규칙은 quant 한 곳(`accessibleRuleSets`)에 둔다.
- **advisory lock**: 개수 상한은 유니크 제약으로 표현할 수 없다. 사용자 단위 락이라 다른 사용자와 경합하지 않는다.
- **일괄 시계열 + 캐시**: 행마다 요청하면 50행 화면이 50요청이다. 10분 버킷이면 스파크라인 모양은 유지되고 응답이 작다.

## Consequences

- 거래량 배수는 장 초반에 1보다 작게 보인다(당일 누적이 아직 적다). "거래량 배수 2× 이상" 필터는 오전에 거의 비어 있을 수 있다.
- 스크리너의 `volume` 정렬·열은 여전히 최신 1분봉 거래량이다(기존 동작). 일 거래량 기준 정렬은 `volmult`다.
- 퀀트 시그널 조건이 있는 요청은 사용자별로 캐시돼 캐시 적중률이 낮다.
- `saved_screens.criteria`는 JSON이라 조건 필드가 바뀌면 옛 행이 무효가 될 수 있다 — 지금은 목록에서 빠질 뿐 자동 이전은 없다.
- 장중 시계열 창(11시간)은 국내 장(07:30~18:00 틱) 기준으로 잡았다. 해외 종목은 세션이 길어 앞부분이 잘릴 수 있다.
- 섹터는 `stocks.sector` 문자열을 그대로 쓴다. 표준 업종 분류가 아니라 데이터 출처(KRX 마스터·Mock)의 값이다.

## Revisit When

- 휴장일·세션 캘린더가 생기면 — 거래량 배수를 장 경과 시간으로 보정(c)할지 다시 본다.
- 종목 수가 수천 개를 넘어 `minVolMult`·`volmult` 쿼리가 느려지면 — 거래량 배수를 일봉 집계 때 미리 계산해 두는 컬럼/뷰로 옮긴다(scale-out-plan).
- 저장 조건을 공유하거나 알림 규칙으로 쓰고 싶어지면 — 지금은 개인용 필터일 뿐이다.
