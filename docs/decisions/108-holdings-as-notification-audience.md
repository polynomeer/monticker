# ADR-108: 종목 소식의 받는 사람을 "관심종목 ∪ 모든 실계좌의 보유 종목"으로 넓힌다

## Status
Accepted

[ADR-100](100-watchlist-news-disclosure-alerts.md)(뉴스·공시 팬아웃)과 `StockEventWriter`의 감지 이벤트 푸시는 받는 사람을 정하는 쿼리만 바뀐다.
나머지 결정은 그대로 따른다: 시간당 상한·신선도(ADR-100), 발송 직전 설정 적용(ADR-082), 방해 금지 시간(ADR-093).
기존 결정을 번복하지 않는다. [ADR-106](106-account-aggregation-staged-sources.md) 1단계의 "보유 기준 피드·알림" 항목이다.

## Context

종목 소식(급등·급락·거래량 급증 감지, 뉴스, 공시)은 지금까지 그 종목을 **관심종목에 넣은** 사용자만 받았다. 1단계에서 이용자가
손 입력과 CSV로 여러 증권사 계좌의 거래를 넣을 수 있게 됐다. 실제로 돈이 들어간 종목은 관심종목에 없을 수 있다. 계획
([account-aggregation-plan.md](../account-aggregation-plan.md))은 피드·알림 기준을 "내가 가진 종목(모든 계좌)"으로 넓히는 것을 1단계 MVP로 잡았다.

정해야 할 것:

1. **보유를 어떻게 넣나.**
   - (a) 보유 종목을 관심종목 그룹("보유 종목")에 자동으로 넣고 지운다. 받는 사람 쿼리는 그대로다. 대신 거래가 바뀔 때마다 동기화해야 한다.
     이용자가 만든 그룹과 섞이고, Watch Rule GROUP 대상(ADR-095)에도 영향이 간다.
   - (b) 받는 사람 쿼리에서 원장(portfolio_transactions)으로 보유를 바로 판정해 관심종목과 합친다 — 채택.
2. **"보유"의 기준.** 화면의 보유(`HoldingsCalculator`)와 같아야 한다. 알림을 받았는데 "내 자산"에 그 종목이 없으면 안 된다.
   단순 합계(매수 − 매도)는 앞 구간이 빠진 CSV에서 계산기와 어긋난다. 계산기는 가진 것보다 많이 판 매도를 0에서 멈추기 때문이다.
3. **모의계좌.** 모의 자금이다. 넣으면 모의 매매만 해도 실제 보유처럼 알림이 온다.
4. **끄는 방법.** 보유 알림만 따로 끄는 설정을 둘지.

## Decision

**받는 사람 = 관심종목 ∪ 보유.** 소식을 보내는 두 경로가 worker의 `StockAudience.INTERESTED_USERS_SQL` 하나를 쓴다.

```
감지 이벤트 푸시 (StockEventWriter)          뉴스·공시 팬아웃 (NewsAlertFanout, ADR-100)
        └──────────────┬──────────────────────────┘
                       ▼
     StockAudience.INTERESTED_USERS_SQL (stockId)
       watchlist_items ⋈ watchlist_groups
       UNION
       portfolio_transactions ⋈ portfolio_accounts  — 계좌·통화별 보유 수량 > 0
                       ▼
     탈퇴 제외 · 알림 설정(ADR-082) · 상한(ADR-100) · 방해 금지(ADR-093) — 기존 그대로
```

- **보유 판정은 계산기와 같은 규칙이다.** 계좌·통화별로 (거래일, id) 순서로 매수 +, 매도 −를 더한다. 매도가 가진 수량을 넘으면 0에서 멈춘다.
  0에서 멈추는 누적합의 마지막 값은 `합계 − min(0, 누적합의 최솟값)`이다. 그래서 창 함수 한 번으로 계산기와 같은 값을 낸다.
  계좌끼리, 통화끼리 상계하지 않는다(계산기도 계좌마다, (종목, 통화)마다 계산한다).
- **모의계좌는 넣지 않는다.** portfolio 원장만 본다.
- **따로 끄는 설정은 두지 않는다.** 기존 종류별 설정(가격 알림·거래량 급증·뉴스·공시)이 관심종목과 보유에 똑같이 적용된다.
  보유 기준 알림을 원하지 않으면 그 종목의 거래를 지우거나 "내 자산 데이터 전체 삭제"를 쓴다.
- **피드:** `GET /api/portfolio/events`가 같은 기준(`PortfolioHoldingsQueryService.heldStockIds`, 계산기 그대로)의 종목 이벤트를
  최신순으로 준다. 커서는 (시각, id)이다. 시각만으로 자르면 같은 시각 이벤트가 페이지 경계에서 빠진다.
- **인덱스:** V106 `idx_portfolio_tx_stock_trade (stock_id, account_id, trade_date, id) WHERE stock_id IS NOT NULL AND type IN ('BUY','SELL')`.
  소식 하나마다 그 종목의 매매 행만 읽는다.

## Reasons

- (b)는 동기화가 없다. 거래를 넣거나 되돌리거나 지우면 다음 소식부터 바로 반영된다. 계좌 삭제·전체 삭제(동의 철회)도 따로 할 일이 없다.
  (a)는 거래 변경 경로(손 입력·CSV 확정·되돌리기·삭제)마다 그룹을 맞춰야 하고, 하나라도 빠지면 철회한 사람에게 알림이 간다.
- 화면 보유와 알림 대상이 같은 규칙이라 "알림은 왔는데 내 자산에 없다"가 생기지 않는다. api 계산기와 worker SQL이 같은지는
  양쪽 테스트가 같은 사례(먼저 판 기록, 같은 날 순서, 계좌·통화 분리)로 고정한다.
- 따로 끄는 설정은 지금 근거가 없다. 소식의 양은 이미 종류별 설정과 시간당 상한이 묶는다. 보유 종목은 관심종목보다 보통 적다.

## Consequences

- **동의 문구의 목적에 "보유 종목 소식 알림·피드"가 들어가야 한다.** 계좌는 "계좌 정보 수집·이용" 동의가 있어야 만들어진다.
  확정 문구(아직 초안 버전)에 이 이용 목적을 적는다([human-action-items.md](../human-action-items.md)).
- 받는 사람이 늘어 푸시·알림 이력 행이 늘어난다. 뉴스는 ADR-100의 사용자별 시간당 상한이 그대로 묶는다.
  감지 이벤트 푸시에는 상한이 없다. 지금처럼 탐지기의 중복 방지(분 단위 유니크)만 받는다.
- api와 worker가 같은 규칙을 두 번 구현한다(Kotlin 계산기, SQL 창 함수). 계산기 규칙을 바꾸면 `StockAudience`도 바꿔야 한다.
  두 클래스의 주석이 서로를 가리킨다.
- 소식마다 그 종목의 전체 매매 기록을 창 함수로 훑는다. 이용자·거래가 많아지면(종목당 수만 행) 비용이 커진다.
- 알림 문구는 관심종목과 보유를 구분하지 않는다("monticker 이벤트 알림").

## Revisit When

- 종목당 매매 행이 수만을 넘어 받는 사람 쿼리가 소식 처리 지연(ADR-045 SLO)에 보이면 — 계좌·종목별 보유 수량을 캐시 테이블로 둔다
  (거래 변경 시 갱신).
- 이용자가 보유 알림만 따로 끄고 싶다는 요청이 반복되면 — `notification_preferences`에 출처(관심종목/보유) 축을 더한다.
- 2단계(증권사 API 잔고)·3단계(마이데이터)에서 보유가 원장이 아니라 잔고 스냅샷으로 정해지면 — 판정 출처를 다시 정한다.
- 모의계좌 보유도 소식을 받고 싶다는 요청이 있으면.
