# ADR-045: 성능·정합성 검증 기준 — SLO 정의와 하네스 범위

## Status
Accepted

## Context

[scale-out-plan.md](../scale-out-plan.md)의 Phase 0 항목 7건은 전부 "이렇게 하면 빨라진다 /
안 깨진다"는 주장이다. **그 주장을 검증할 기준선이 없다.**
개선을 증명할 수 없으면 개선했는지 알 수 없고, 회귀도 감지하지 못한다.

### 지금 있는 것

`bench/`에 k6 하네스가 있다.

```
bench/run.sh          smoke | load | stress | spike 4개 프로파일
bench/scenarios/api.js  175줄
bench/compare.sh      두 결과 JSON 비교
bench/results/        smoke_2026-06-24T00-19-10.json, latest_smoke.json
```

| 프로파일 | 최대 VU | 임계값 |
|---------|--------|-------|
| smoke | 3 | — |
| load | 50 | p95 < 300ms, p99 < 500ms |
| stress | 100 | p95 < 1000ms |
| spike | 100 (급증) | — |

### 무엇이 빠졌나

**1) REST 4개 엔드포인트만 때린다.** `stocks/search`, 캔들, 종목 상세, `events/recent`.
주문·지갑·스크리너·퀀트는 없다.

**2) WebSocket이 전혀 없다.** [scale-out-plan §1.2](../scale-out-plan.md)가 계산했듯
**fan-out이 가장 과소평가된 축**인데, 하네스에 동시접속 개념 자체가 없다.
[ADR-038](038-broadcast-consumer-partition-assignment.md)·[ADR-039](039-drop-global-market-topic.md)가
고치려는 결함이 정확히 이 영역이고, 지금 하네스로는 **고치기 전후를 비교할 수 없다.**

**3) 틱 유입 부하가 없다.** 파이프라인 처리량(`market.ticks` → 캔들 → 이벤트 → 알림)을
재는 수단이 없다. [ADR-040](040-kafka-topic-declaration.md)의 파티션 산정 근거
("파티션당 ~2,000 msg/s")도 **가정일 뿐 실측이 아니다.**

**4) 정합성 검증이 없다.** 임계값이 전부 `http_req_duration`/`http_req_failed`다.
"부하 중에 잔고가 맞는가", "캔들이 유실되지 않았는가"를 확인하지 않는다.
[ADR-043](043-ledger-pagination-and-reconciliation.md)이 도입하는 대사(reconciliation)와
[ADR-041](041-timescale-hypertable-promotion.md)이 경고하는 캔들 flush 실패가
정확히 이 범주다.

**5) 실행 기록이 사실상 없다.** `bench/results/`에는 2026-06-24 smoke 1건뿐이다.
load/stress/spike는 결과 파일이 없다 — **정의만 있고 돌린 적이 없다.**

## Decision

### 1. 워크로드 클래스별 SLO를 정의하고, 이것을 Phase 완료 게이트로 삼는다

[scale-out-plan §5](../scale-out-plan.md)의 4개 클래스에 각각 수치를 확정한다.

| 클래스 | 지표 | 목표 | 실패 시 의미 |
|--------|------|------|------------|
| **실시간** | 틱 생성 → 브라우저 수신 p99 | < 300ms | 시세가 늦다 |
| | 컨슈머 랙 (`market.ticks`) | < 5s | 파이프라인이 못 따라간다 |
| | 메시지 유실률 (conflation 제외) | 0 | 특정 종목이 갱신 안 된다 |
| **거래** | 주문 접수 → 응답 p99 | < 500ms | 주문이 느리다 |
| | **잔고 정합성 오차** | **0** | **돈이 틀린다** |
| | 중복 체결 / Saga 미완료 | 0 | 자금 사고 |
| **조회** | REST p95 / p99 | < 200ms / < 500ms | 화면이 느리다 |
| | 에러율 | < 0.1% | |
| **분석** | 백테스트 큐 대기 포함 p95 | < 60s | 사용자가 기다린다 |
| | 분석 부하가 거래 경로에 준 영향 | 0 | bulkhead가 샜다 |

> **트리거 지표(§7)와 SLO는 다르다.** 트리거는 "언제 착수하나"(동접 1,000 초과 등),
> SLO는 "끝났나"다. 두 개를 섞으면 "부하가 늘었으니 일단 스케일아웃"이라는,
> 병목을 확인하지 않은 대응으로 흐른다.

### 2. 도구를 워크로드별로 나눈다 — k6 하나로 전부 하지 않는다

| 시나리오 | 도구 | 이유 |
|---------|------|------|
| `rest-*` (조회·주문 API) | **k6** (기존 확장) | 이미 있고, HTTP에 적합 |
| `ws-fanout` (동접·구독) | **k6 `ws` 모듈 + 수동 STOMP 프레이밍** | 아래 주 참고 |
| `tick-storm` (틱 유입) | **Go 부하 생성기** (`services/market-gateway` 재사용) | k6로 Kafka 프로듀서 부하를 만들 수 없다 |
| `consistency-*` (정합성) | **JUnit + Testcontainers** | 부하와 독립적으로 재계산·대조해야 한다 |

> **STOMP over SockJS 주의**: 클라이언트는 SockJS로 붙지만, Spring의 `withSockJS()`는
> raw WebSocket 트랜스포트를 `/ws/websocket`에도 노출한다. k6의 `ws` 모듈로 거기에 붙어
> STOMP 프레임(`CONNECT`/`SUBSCRIBE`/`MESSAGE`)을 직접 만들면 SockJS 핸드셰이크를
> 구현하지 않아도 된다. **단 이건 프로덕션 클라이언트와 다른 경로**이므로,
> SockJS 폴백 경로의 부하 특성은 별도로 확인해야 한다.

### 3. 정합성 검증 하네스를 만든다 — 성능 수치보다 이게 중요하다

부하 시나리오와 짝을 이루는 **독립 재계산 대조** 스크립트를 만든다.
"부하를 견뎠는가"가 아니라 "부하 중에 틀리지 않았는가"를 본다.

| 검증 | 방법 |
|------|------|
| 잔고 | 부하 종료 후 `paper_accounts.cash` vs `SUM(ledger_events.amount)` ([ADR-043](043-ledger-pagination-and-reconciliation.md)의 대사 로직 재사용) |
| 캔들 | `candles_1m` vs 부하 생성기가 발행한 틱을 독립적으로 집계한 결과 |
| 주문 | 접수 건수 = FILLED + CANCELLED + PENDING, 중복 `fills` 0 |
| 이벤트 | 생성된 `stock_events`에 중복(dedup 인덱스 위반 회피분) 없음 |
| Saga | `order_sagas`에 STARTED/COMPENSATING 잔류 0 |

### 4. Phase 0 착수 전에 기준선을 측정한다

각 Phase 0 항목의 **전후를 같은 시나리오로 비교**한다. `bench/compare.sh`가 이미
두 결과 JSON을 비교하므로 기록 형식은 그대로 쓴다.

측정 순서:
```
1. 확장된 시나리오로 현재(커밋 5d788b2) 기준선 측정 → bench/results/baseline_*.json
2. Phase 0 항목 적용
3. 같은 시나리오 재측정 → compare.sh로 대조
4. ADR의 주장과 실측이 다르면 ADR을 고친다 (예: ADR-040의 "파티션당 2,000 msg/s")
```

### 5. 실행 환경을 명시한다 — 로컬 수치를 절대값으로 쓰지 않는다

| 환경 | 무엇을 재는가 | 무엇을 재지 못하는가 |
|------|-------------|-------------------|
| 로컬 (docker-compose, 개발 머신) | **상대 비교** (전/후), 정합성, 기능적 회귀 | 절대 처리량, 네트워크 지연, 디스크 I/O 특성 |
| 전용 부하 환경 (K8s, prod 유사) | 절대 수치, 용량 산정, SLO 판정 | — |

**Phase 0의 기준선은 로컬에서 잡는다.** 절대값이 아니라 "고쳤더니 나아졌는가"를 보는
용도이고, 전용 환경 구축을 기다리면 Phase 0이 시작조차 못 한다.
**SLO 판정(§1)은 전용 환경에서만 유효**하며, 이는 Phase 1의 선행 작업이다.

### 6. CI에는 smoke만 넣는다

`load`/`stress`/`ws-fanout`/`tick-storm`은 시간이 오래 걸리고 결과가 실행 환경에
민감하다. PR마다 돌리면 플레이키해져 곧 무시된다. CI는 **smoke(기능적 회귀 감지)만**
돌리고, 나머지는 수동/야간 실행으로 둔다.

## Reasons

- **기준선 없는 최적화는 검증이 아니라 믿음이다.** Phase 0의 7개 항목은 전부 "이게 병목"
  이라는 코드 근거를 갖고 있지만, 효과의 크기는 아무도 모른다. 특히
  [ADR-038](038-broadcast-consumer-partition-assignment.md)의 conflation처럼 사용자에게
  보이는 동작을 바꾸는 변경은 "얼마나 이득인지"를 수치로 말할 수 있어야 한다.
- **정합성 검증을 성능보다 앞에 두는 이유**: 느린 건 사용자가 불평하고 끝나지만,
  틀린 잔고는 되돌릴 수 없다. CLAUDE.md가 명시한 대로 이 프로젝트는 실제 자금이 오갈
  예정이고, 그렇다면 "부하 중에도 돈이 맞는가"가 p99보다 중요한 통과 조건이다.
- **k6 하나로 통일하지 않는 이유**: k6는 HTTP/WS 클라이언트 부하 도구다.
  Kafka 프로듀서로 초당 수만 건을 밀어넣는 건 도구의 용도 밖이고,
  억지로 맞추면 하네스 자체가 병목이 된다. 반대로 REST 부하를 Go로 다시 짜는 것도
  이미 있는 k6를 버리는 낭비다. **도구를 나누는 비용보다 억지로 합치는 비용이 크다.**
- **로컬 기준선을 인정하는 이유**: "제대로 된 부하 환경을 먼저 만들자"는 옳지만,
  그걸 선행 조건으로 걸면 이미 확인된 버그(ADR-038의 틱 유실 등)의 수정이 인프라 작업에
  묶인다. 상대 비교만으로도 "고쳤다"는 확인은 가능하다.
- **CI에 무거운 부하 테스트를 넣지 않는 이유**: 이 저장소에는
  [빨간 CI로도 머지된 전례](../engineering-backlog.md)가 있다. 플레이키한 게이트는
  게이트가 아니라 무시 대상이 된다. 신뢰할 수 있는 것만 CI에 넣는다.

## Consequences

- **`bench/`가 커진다.** 시나리오 1개(`api.js`)에서 최소 5개로 늘고, Go 부하 생성기와
  정합성 검증 모듈이 추가된다. `bench/README.md`를 함께 갱신한다.
- **부하 생성기가 프로덕션 코드를 재사용한다.** `services/market-gateway`를 부하 모드로
  돌리면 "생성기의 버그가 프로덕션 경로의 버그이기도 하다"는 이점이 있는 반면,
  부하 전용 코드가 프로덕션 서비스에 섞일 위험이 있다. **별도 빌드 태그/프로파일로
  격리**하고, 부하 전용 코드가 기본 빌드에 포함되지 않게 한다.
- **SLO 수치는 지금 근거가 약하다.** §1의 값들은 업계 통념과 사용자 체감에서 잡은
  출발점이지 실측 기반이 아니다. **기준선 측정 후 조정하는 것을 전제**로 한다 —
  달성 불가능한 목표를 박아두면 SLO가 무시된다.
- **정합성 검증이 실패를 새로 드러낼 것이다.** 지금까지 확인한 적이 없으므로,
  첫 실행에서 기존 드리프트가 나올 가능성이 높다([ADR-043](043-ledger-pagination-and-reconciliation.md)의
  대사와 같은 상황). 이건 하네스의 버그가 아니라 하네스가 일한 것이다.
- **전용 부하 환경 구축이 Phase 1의 명시적 항목이 된다.** 지금까지 로드맵에 없었다.
- 기존 `load`/`stress`/`spike` 프로파일의 임계값(p95 < 300ms 등)은 §1의 조회 클래스
  SLO와 맞춘다 — 두 곳에 다른 숫자가 있으면 안 된다.

## Revisit When

- **기준선 측정 직후** — §1의 SLO 수치를 실측에 맞게 조정한다. 이건 예외가 아니라 계획이다.
- **전용 부하 환경이 생겼을 때** — 로컬/전용 환경 수치의 차이(배율)를 기록해두면,
  이후 로컬 측정만으로도 대략의 절대값을 추정할 수 있다.
- **Phase 2의 매칭 엔진 샤딩 착수 전** — 자금 정합성이 걸린 변경이므로
  섀도 모드(실주문 없이 병렬 실행 후 결과 비교) 하네스가 추가로 필요하다.
  §3의 정합성 검증이 그 토대가 된다.
- **부하 테스트가 3개월 이상 실행되지 않았을 때** — 지금이 정확히 그 상태다
  (마지막 결과 2026-06-24). 하네스는 돌지 않으면 썩는다. 야간 정기 실행을 검토한다.
