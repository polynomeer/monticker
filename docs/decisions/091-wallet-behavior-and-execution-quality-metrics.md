# ADR-091: 지갑 행동 지표(계획·손절 준수율, 지난주 대비, 날짜별 수익률)와 모의 체결 품질(슬리피지·지연)의 정의

## Status
Accepted

## Context

[design-rollout-plan.md](../design-rollout-plan.md) §3의 P2 항목 네 개가 화면에 `—`로 남아 있었다.

1. /wallet 점수 카드 세부 지표 — 계획 준수율, 손절 준수율, 지난주 대비
2. /wallet/replay "감정 분포 · 이번 주"와 날짜별 % — 감정 분석은 전체 기간만, 날짜 띠는 손익 금액만(날짜마다 리플레이 API 6번)
3. /matching 상단 평균 슬리피지·지연 — 주문 시점 호가를 남기지 않아 계산할 근거가 없음

숫자를 만들기 전에 **무엇을 세는지**를 정해야 한다. 이 지표들은 행동을 돌아보는 피드백이며, 정의가 모호하면 같은 기록이
화면마다 다른 숫자로 보이고, 조작 가능한 입력이 섞이면 지표가 의미를 잃는다(ADR-085가 출처를 서버 경로로 정한 이유).

고려한 대안:

- **손절 준수율 기준**: (a) 손실 매도 전체 중 "손절가 이하에서 판 것" — 손절을 정하지 않은 거래까지 실패로 센다. 기각.
  (b) **손절을 정해 둔 포지션의 손실 매도만** 세고 처음 정한 손절선과 비교 — 채택. (c) 가장 최근 손절과 비교 — 손절을
  내려 놓고 그 가격에 판 경우가 "지킴"이 되어 지표가 무의미해진다. 기각.
- **날짜별 수익률의 평가자산**: (a) 일별 스냅샷 테이블을 새로 쌓는다 — 과거 날짜가 없고 배치가 하나 늘어난다.
  (b) **원장(현금) + 체결(수량) + 1분봉(가격)에서 조회 시점에 재구성** — 채택. 대사 불변식(ADR-043)이 이미 "현금 + 예약금 =
  초기 지급 + 원장 합"을 보장한다.
- **접수 시점 호가**: (a) 화면이 보던 호가를 요청에 실어 보낸다 — 클라이언트 입력이라 조작 가능. 기각.
  (b) Yahoo·Mock 호가도 기록 — 최우선 호가 자체가 현재가에서 지어낸 값이라 슬리피지가 항상 같은 숫자가 된다. 기각.
  (c) **서버가 사가 안에서 KIS 실시간 호가(Redis 캐시)만 기록** — 채택.

## Decision

모든 기간은 **KST 날짜**다. 경계(00:00 KST)는 Kotlin `KstPeriod`(common)가 계산해 `Instant`로 바인딩한다 — SQL의
`AT TIME ZONE`이나 JVM 기본 시간대에 기대지 않는다(통합 테스트를 `-Duser.timezone=UTC`로도 돌린다). 주는 **월요일 00:00 ~
다음 월요일 00:00 KST**. 기간 파라미터(`from`·`to`, 양 끝 포함)는 함께 주거나 함께 생략하고, `from > to`나 1년 초과는 400.

### 1. 점수 카드 세부 지표 — `GET /api/wallet/score`의 `details`

| 지표 | 정의 | 분모 0 |
|---|---|---|
| 계획 준수율 | ADR-085 "계획된 주문" — `ReplayService.isPlanned` **같은 함수**. 이번 주 체결(매수·매도) 중 계획 ÷ 판정 가능 | `—` |
| 손절 준수율 | 아래 | `—` |
| 지난주 대비 | 위 두 비율은 이번 주 − 지난주(%p), 행동 점수는 이번 주 평균 − 지난주 평균(그 주에 계산된 일별 점수 평균) | 한쪽이 없으면 `—` |

"이번 주" = 이번 주 월요일 00:00 KST부터 지금까지, "지난주" = 직전 월~일 전체.

**손절 준수율**

```
대상(분모)  = 기간 안의 손실 매도(이동평균 실현 손익 < 0, ADR-085 RealizedPnlCalculator)
              중 그 포지션에 손절을 정해 둔 것
포지션의 손절(기준 손절)
            = 같은 사용자·같은 종목의 STOP_LOSS 모의 조건부 주문(ADR-075) 가운데
              positionSince ≤ 등록 시각 ≤ 매도 시각 인 것 중 가장 먼저 등록한 것
              (상태 무관 — 정했다가 취소한 손절도 "정한 손절"이다)
positionSince = 그 포지션이 열리기 직전에 보유가 마지막으로 0이 된 체결 시각(없으면 처음부터)
지킴        = 기준 손절이 직접 발동해 나간 매도(출처 CONDITIONAL, ref = 기준 손절 — 갭으로 손절가 아래 체결돼도)
              또는 매도 가격 ≥ 기준 손절가
못 지킴     = 그 밖(손절가 아래에서 직접 팔았거나, 손절을 내리거나 지운 뒤 더 떨어져 판 경우)
손절을 정하지 않은 손실 매도는 분모에서 뺀다.
```

`positionSince`를 하한으로 두는 이유: "체결 시 자동 등록" 손절은 부모 매수 **체결 전에** 등록된다. 매수 시각을 하한으로 쓰면
이 손절이 빠진다. 반대로 이전 포지션에서 정한 손절은 하한 밖이라 섞이지 않는다.

### 2. 감정 분포 기간 — `GET /api/wallet/emotion-analysis?from&to`

- 기간은 **거래 체결 시각** 기준(태그를 남긴 시각이 아니다). 생략하면 전체 기간(기존 동작).
- 응답에 감정별 `sharePct`(구간 안 태그된 거래 중 비중)와 `totalCount`. 평균 수익률은 기존 정의 그대로: 매수 태그만,
  (그 뒤 같은 종목 첫 매도가 − 매수가) ÷ 매수가.
- 태그·거래·첫 매도가를 **한 쿼리**(LATERAL)로 읽는다. 이전엔 태그마다 거래 조회 + 매도가 조회(N+1). 태그 소유자 = 거래 소유자.
  레이트 리밋을 시간당 10 → 60회로 올렸다(리플레이가 주를 바꿀 때마다 부른다).

### 3. 날짜별 수익률 — `GET /api/wallet/daily-returns?from&to` (생략 시 최근 7일, 최대 1년)

```
평가자산(t) = 현금 + 예약금 + 보유 평가액   ← /wallet 총자산과 같은 정의
  현금 + 예약금(t) = 초기 지급(initial_capital) + Σ 현금 영향 원장(CASH_EVENT_TYPES, created_at < t)   ← ADR-043 불변식
  보유 평가액(t)   = Σ 종목별 (t 이전 체결의 순수량) × (t 직전 1분봉 종가)
날짜 d의 손익     = 평가자산(d+1 00:00, 오늘이면 지금) − 평가자산(d 00:00) − 그날 입출금(DEPOSIT·WITHDRAWAL)
날짜 d의 수익률   = 손익 ÷ 평가자산(d 00:00) × 100
```

계산하지 않는 날(상태로 알려 준다, 화면 `—`): 그날이 끝나기 전에 계좌가 없었다(`NO_ACCOUNT`), 그날 시작 이후 초기화가 있었다
(`RESET` — 초기화는 체결 기록을 지워 그 이전 보유를 되살릴 수 없다), 들고 있던 종목의 시세가 없다(`NO_PRICE`), 시작 평가자산 ≤ 0
(`NO_EQUITY`). 미래 날짜는 응답에 없다.

쿼리 수는 날짜·종목 수와 무관하다: 계좌 1, 원장 3(마지막 초기화·구간 이전 합·구간 행), 체결 2(구간 이전 종목별 합·구간 행),
종가 1(필요한 (종목, 경계) 쌍을 배열로 넘겨 `unnest` + LATERAL — 경계는 epoch ms).

### 4. 모의 체결 품질 — `GET /api/matching/execution-quality?from&to` (체결 시각 기준, 생략 시 최근 30일)

**V88**: `orders`에 nullable `quote_bid`·`quote_ask`·`quote_at`·`quote_source`·`submitted_at`.

- 사가 진입 순간 `submitted_at`을 잰다(검증·현금 예약 전). 종목 확인 직후 `BestQuoteSource`(common 포트, marketdata 구현
  `KisBestQuoteSource`)로 최우선 호가를 읽어 주문 행에 남긴다. **KIS 실시간 호가만**, 30초보다 오래된 스냅샷·빈 호가는 기록하지
  않는다. 조회 실패는 삼키고 주문은 진행한다(Redis GET 1번 + 종목 조회 1번, 네트워크 호출 없음).
- matching은 marketdata에 의존할 수 없어(Modulith) 포트를 common에 둔다.

```
슬리피지(bps, 체결 1건) — 접수 시점 반대편 최우선 호가 대비
  BUY  : (체결가 − ask) ÷ ask × 10,000
  SELL : (bid − 체결가) ÷ bid × 10,000
  양수 = 불리(더 비싸게 사고 더 싸게 팜), 음수 = 유리(가격 개선)
평균 슬리피지 = 수량 가중 평균. 방향별·주문 유형별 분해도 준다.
  그 방향 호가 기록이 없는 체결(V88 이전 주문, 실시간 호가 없음)은 빼고 excludedNoQuote로 센다.
엔진 지연 = 시장가 주문의 첫 체결 filled_at − submitted_at (ms). 평균·p50·p95(nearest-rank).
  지정가는 호가 대기 시간이 섞여 지연에서 뺀다(슬리피지에는 넣는다 — 도착가 대비 개선/악화).
  submitted_at이 없는 주문(V88 이전)은 빼고 excludedNoSubmitTime으로 센다.
```

화면은 평균 슬리피지와 지연 **중앙값**을 보이고, 집계·제외 건수를 툴팁에 적는다. 기록이 없으면 `—`.

## Reasons

- 계획 준수율은 리플레이와 **같은 함수**를 불러 두 화면이 같은 숫자를 낸다(규칙을 복제하지 않는다).
- 손절 준수율은 사용자가 **스스로 정한 손절**만 기준으로 삼는다. 손절이 없던 거래를 실패로 세지 않고, 처음 정한 선을 기준으로
  해서 "손절을 내리고 지켰다고 보이는" 경우를 막는다. 계산 재료(실현 손익·포지션 구간)는 ADR-085의 이동평균 계산기 하나를 쓴다.
- 날짜별 수익률은 이미 대사로 검증되는 원장과 체결에서 재구성해 새 테이블·배치가 없다. 평가자산 정의가 /wallet 총자산과 같아
  "오늘" 끝 값이 지갑 화면 총자산과 맞는다(대사 불일치가 없다면).
- 슬리피지 기준 호가를 서버가 실데이터로만 남겨 조작·지어낸 값이 섞이지 않는다. 기록이 없으면 빼고 그 수를 보여 준다.

## Consequences

- 세부 지표·날짜별 수익률은 조회 때 계산한다(저장하지 않음). 사용자당 체결이 매우 많으면 손절 준수율의 실현 손익 계산(해당 종목
  전체 체결)과 날짜별 수익률의 구간 체결 읽기가 무거워진다.
- wallet이 `paper_conditional_orders`·`paper_trades`·`candles_1m`을 JDBC로 읽는다(읽기 전용, 기존 행동 점수와 같은 방식).
  테이블 구조를 바꾸면 함께 고쳐야 한다.
- 원장 FILL은 체결 커밋 뒤 리스너가 쓰므로 체결 시각보다 수 ms 늦다. 자정 직전 체결은 드물게 현금과 수량이 다른 날로 갈려 그 두
  날의 수익률이 반대로 조금 흔들릴 수 있다.
- 개발·Mock 환경에는 KIS 실시간 호가가 없어 슬리피지는 항상 `—`(제외 건수만 보인다). 지연은 기록된다.
- 엔진 지연은 사가 안의 처리 시간이다(검증·예약·체결). 네트워크·커밋 시간은 들어가지 않는다.
- 감정 분석의 기간 생략 = 전체 기간은 하위 호환으로 남겼다(1년 상한은 기간을 줄 때만).
- `/api/wallet/score`의 점수 날짜를 서버 시간대(`LocalDate.now()`)에서 KST로 고쳤다. UTC 서버에서 KST 00~09시에 전날 점수를
  보이던 결함이다.

## Revisit When

- 모의 주문이 호가창에서 실제로 매칭되게 될 때(ADR-048, scale-out §6.8) — 슬리피지 기준을 "체결 직전 호가"로 바꿀지 검토.
- 조건부 손절에 트레일링·지정가 손절이 생길 때 — 기준 손절의 정의를 함께 갱신한다.
- 사용자당 체결 수가 커져 조회 시점 계산이 느려질 때 — 일별 평가자산 스냅샷(대사 배치에 얹기)과 실현 손익 저장으로 바꾼다.
- 실전 계좌(brokerage_orders)에도 체결 품질을 보이기로 할 때.
