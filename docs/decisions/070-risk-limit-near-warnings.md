# ADR-070: 리스크 한도 근접 경고(80%) — 주기 평가와 하루 한 번 보장

## Status
Accepted

## Context

리스크 게이트([ADR-025](025-real-brokerage-order-safety-gate.md))는 한도를 넘는 매수를 **주문 순간에** 막는다. 사용자는 막히고 나서야
한도에 다가가고 있었다는 사실을 안다. 알림 설정 화면에는 "리스크 경고 — 한도 80% 도달" 항목이 시안으로만 있었다.
VaR·집중도·일일 손실은 주문이 없어도 가격과 체결에 따라 움직이므로, 주문 경로에 붙여서는 알릴 수 없다. 주기 평가가 필요하다.

고려한 대안:
1. **주문·체결 이벤트마다 평가** — 가격 변동만으로 사용률이 오르는 경우(VaR·집중도)를 놓친다.
2. **틱마다 평가(시세 스트림 구독)** — 정확하지만 api 인스턴스가 사용자×틱만큼 DB를 친다. 경고 용도에 비해 과하다.
3. **주기 평가 + 대상 축소 + DB 키로 하루 한 번** — 채택.

## Decision

- `RiskLimitNearWarningJob`(risk 모듈)이 5분 간격(`app.risk.near-limit.interval-ms`)으로 돈다.
- **대상**: 모의계좌 보유 종목이 있거나 오늘(KST) 매도한 사용자, 탈퇴자 제외. 보유도 매도도 없으면 세 규칙 사용률이 모두 0이다.
- **규칙과 기준**(`PaperRiskUsage`) — 매수 게이트와 같은 입력·분모를 쓴다.
  - 1일 VaR: `RiskRuleQueryService.historicalVaRPct`(게이트에서 추출해 공유) / `var_limit_pct`
  - 단일 종목 집중도: 최대 보유 평가액 / (현금 + 보유 평가액) / `concentration_limit_pct`
  - 일일 손실: 오늘 실현 손실 / 현금 / `daily_loss_limit_pct`(모의투자 게이트의 기준 금액이 현금)
  - 섹터 집중도: 섹터 한도를 설정한 경우만(ADR-069)
  - 가격을 모르는 보유가 있으면 집중도류는 건너뛴다. 경고는 주문을 막지 않으므로 "모르면 막는" 게이트와 달리 근거 없는 경고를 내지 않는다.
- **하루 한 번**: `risk_limit_warnings (user_id, rule, kst_date)` PK. 사용률 ≥ 80%인 규칙마다
  `INSERT … ON CONFLICT DO NOTHING`을 하고, 행이 들어간 트랜잭션 안에서만 `UserNotificationCommand`를 발행한다(ADR-065 아웃박스).
  `dedupKey = risk-limit-near:{userId}:{rule}:{yyyy-MM-dd}` — worker 쪽 SETNX와 이중으로 중복을 막는다.
- 리스크 체크를 끈 사용자(유효 한도 기준, ADR-069)는 평가하지 않는다.
- 실거래 계좌는 평가하지 않는다.
- 지난 기록은 매일 04:20 KST에 7일 넘은 것을 지운다.

## Reasons

- 알림 한 번 보장이 DB 제약 하나로 끝난다. api 인스턴스가 여러 대여도(분산 락이 없다) 같은 사용자를 동시에 평가하면 한 곳만 INSERT에 성공한다.
  분산 락(ShedLock 등)을 들이지 않아도 정확하다. 중복 평가 비용만 생긴다.
- 알림 발행과 "보냈다" 기록이 같은 트랜잭션이다. 커밋이 실패하면 둘 다 없고 다음 주기에 다시 시도한다.
- 게이트와 같은 계산을 공유하므로 "경고는 80%라는데 게이트는 이미 막는다" 같은 불일치가 없다.

## Consequences

- 대상 선정이 `paper_trades` 전체 GROUP BY다. 거래 기록이 커지면 비싸진다. 보유 테이블(포지션 스냅샷)이 생기면 그쪽으로 바꾼다.
- 다중 인스턴스에서는 같은 평가가 인스턴스 수만큼 돈다(알림은 한 번).
- 실거래 계좌는 근접 경고가 없다. 사용률을 알려면 증권사 잔고 API를 주기적으로 불러야 하고, 호출 한도(KIS 초당 제한)를 주문 경로와 나눠 쓴다.
- 사용자 알림 설정(끄기)을 아직 보지 않는다(ADR-065와 같음). 알림 `data.type = RISK_LIMIT_NEAR`로 구분해 두었으니 설정 연동 때 이 값으로 거른다.
- 하루 한 번이라, 오전에 80%를 넘었다가 내려간 뒤 오후에 한도를 넘어도 다시 알리지 않는다. 한도 초과 자체는 주문 시 거부 사유로 보인다.

## Revisit When

- 실거래 계좌의 잔고를 주기적으로 캐시하게 될 때(실거래 근접 경고 추가).
- `paper_trades`가 커져 대상 조회가 느려질 때, 또는 보유 테이블이 생길 때.
- 알림 설정에서 리스크 경고를 끌 수 있게 될 때.
- 단계별(80%·100%) 알림 요구가 생길 때 — 키에 단계를 더한다.
