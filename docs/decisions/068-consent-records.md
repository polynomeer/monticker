# ADR-068: 동의 기록 — 추가 전용 원장, 문서 버전 단위, 화면 게이트

## Status
Accepted

**Note (2026-10-06):** 설정 화면에서 선택 동의(마케팅)를 철회한 뒤 **다시 동의할 길**이 없었다 — `POST /api/users/me/consents`는 가입 필수
묶음(SIGNUP 그룹)만 받는다. `PUT /api/users/me/consents/{type}`을 더했다: 어느 그룹에서도 필수가 아닌 선택 항목만 받고(필수는 400 — 문서
전문을 보여 주는 가입·동의 화면에서만 받는다), 현재 버전으로 이미 동의한 상태면 행을 더 쌓지 않는다. 출처는 `SETTINGS`. 발송 경로가 쓸
`ConsentService.isAgreed(userId, type)`(최신 행이 현재 버전의 동의인가)도 더했다. 첫 사용처는 알림 설정의 "전략 마켓 소식"이다(ADR-082).

## Context

가입 화면에는 약관·개인정보·연령 체크박스가, 증권사 연동 화면에는 위임·자금 미보관·손실 귀속 고지 체크박스가 있다.
그런데 서버는 아무것도 기록하지 않았다. "동의했다"는 증빙이 없다([design-rollout-plan.md](../design-rollout-plan.md) P0-1, P0-2).
빈자리는 두 군데 더 있었다.
- **소셜 가입**(`socialLoginOrSignup`)은 가입 폼을 거치지 않는다. 동의를 받을 지점 자체가 없다.
- 약관은 아직 법률 검토 전 초안이다. 문구가 바뀌면 기존 회원에게 다시 받아야 한다. 무엇에 동의했는지 버전으로 남기지 않으면 개정 여부를 판단할 수 없다.

고려한 대안:
1. **`users`에 동의 컬럼(`terms_agreed_at` 등)을 둔다.** 단순하지만 항목·버전이 늘 때마다 컬럼이 늘어난다. 철회 이력도 남지 않는다.
2. **동의 이벤트를 추가 전용 테이블에 쌓는다** — 채택.
3. **외부 동의 관리 서비스(CMP).** 지금 규모에 과하고, 외부로 개인정보 흐름이 하나 더 생긴다.

## Decision

- `user_consents`(V58): `user_id`, `consent_type`, `document_version`, `agreed`, `source`, `recorded_at`. **추가만 한다.** 철회도 `agreed = false` 행을 덧붙인다. 현재 상태는 항목별 최신 행이다.
- 항목과 그룹은 `common.consent`에 둔다(공용 커널, 모든 모듈이 쓸 수 있다).
  - `SIGNUP`: 필수 TERMS·PRIVACY·AGE_OVER_19, 선택 MARKETING.
  - `BROKERAGE_CONNECT`: 필수 BROKERAGE_DELEGATION·BROKERAGE_NO_CUSTODY·BROKERAGE_LOSS_ATTRIBUTION.
- **문서 버전은 서버가 정한다**(`ConsentDocuments`). 클라이언트는 항목 이름만 보낸다. 약관을 개정하면 버전을 올린다. 그러면 기존 동의는 "현재 버전이 아님"이 되어 다시 받게 된다.
- **같은 트랜잭션에서 검증·기록한다.**
  - 가입: 사용자 저장 → `requireAndRecord`. 필수가 빠지면 400이고, 사용자 행도 롤백된다.
  - 증권사 연동: 증권사 호출 **전에** 검증한다. 연동이 실패하면 기록도 롤백된다.
  - 알 수 없는 항목도 400이다(조용히 버리지 않는다).
- **소셜 가입·약관 개정 게이트.** `GET /api/users/me/consents`가 `missingRequired`를 돌려준다. 앱 화면 골격(`TerminalPage`)이 이것을 보고 `/consent?next=…`로 보낸다. 동의 화면은 `POST /api/users/me/consents`로 받는다. `next`는 앱 내부 상대 경로만 허용한다(열린 리다이렉트 방지).
- 선택 항목(마케팅)만 `DELETE /api/users/me/consents/{type}`으로 철회할 수 있다. 필수 철회는 탈퇴로 처리한다.
- FK는 `users(id)` 기본(RESTRICT)이다. 탈퇴는 소프트 삭제라 증빙이 계정과 함께 사라지지 않는다.

## Reasons

- 추가 전용이면 "언제 어느 버전에 동의했고 언제 철회했나"가 그대로 남는다. 분쟁 시 증빙이 된다.
- 버전을 서버가 정하므로 클라이언트가 옛 화면으로 옛 버전에 동의하는 일이 없다. 개정 시 재동의 대상도 계산만으로 나온다.
- 기록이 행위와 같은 트랜잭션이라 "가입은 됐는데 동의 기록이 없다"는 상태가 생기지 않는다.
- 게이트를 화면 골격에 두면 페이지마다 확인 코드를 넣지 않아도 된다.

## Consequences

- **서버는 동의 없는 사용자의 API 호출을 막지 않는다.** 게이트는 화면 단계다. 실주문은 연동 시 별도 동의가 서버에서 강제되므로, 돈이 움직이는 경로는 서버 기준으로도 막혀 있다. 그 밖의 조회 API까지 막을지는 법률 검토 결과로 정한다.
- 이 변경 전 가입자는 동의 기록이 없다. 다음 접속 때 모두 동의 화면을 거친다(의도된 동작).
- IP·User-Agent는 저장하지 않는다. 증빙 강도를 높이려면 추가할 수 있지만, 그 자체가 수집 항목이라 처리방침 개정이 먼저다.
- `ConsentDocuments` 버전을 올리는 일은 약관 문구 변경 PR의 체크리스트 항목이 된다.

## Revisit When

- 법률 검토에서 IP·기기 정보 등 추가 증빙이나 동의 원문 스냅샷 보관을 요구할 때.
- 동의 없는 사용자의 API 접근을 서버에서도 막아야 할 때. 필터 단계 게이트를 검토한다.
- 마케팅 발송을 실제로 구현할 때. 발송 경로가 최신 MARKETING 상태를 확인해야 한다.
