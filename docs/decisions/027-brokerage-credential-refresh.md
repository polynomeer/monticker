# ADR-027: 증권사 자격증명 재발급/만료 UX 정책

## Status
Accepted

## Context

[ADR-025](025-real-brokerage-order-safety-gate.md)는 KIS 실거래 게이트 도입 당시 "자격증명 재발급/만료 UX 정책은 다음 라운드로 미룬다"고 명시했고, ADR-026도 같은 항목을 재확인만 하고 넘겼다. 지금까지의 실제 동작은 다음과 같았다:

- `BrokerageAccount.isTokenValid()` — accessToken이 있고 `tokenExpiresAt`가 지나지 않았는지만 확인.
- `BrokerageService.requireCredentials()` — 토큰이 만료됐으면 무조건 `IllegalStateException("증권사 토큰이 만료되었습니다. 재연동이 필요합니다.")`을 던진다.
- KIS(`expiresIn`=86400초, 24시간) / Toss(`expires_in`=86400초, 24시간) 모두 **refresh token을 제공하지 않는다** — 만료되면 발급 때와 동일한 엔드포인트(`/oauth2/tokenP`, `/oauth2/token`)를 appKey/appSecret으로 다시 호출해야 한다.

즉 지금 코드는 **appKey/appSecret 자체는 여전히 유효한, 매일 반복되는 정상적인 토큰 만료**조차 "재연동 필요" 에러로 처리해 사용자에게 "계좌 연동" 화면에서 appKey/appSecret을 다시 입력하라고 요구한다. 하지만 appKey/appSecret은 이미 암호화되어 저장돼 있고(ADR-025), 토큰 재발급에 필요한 건 그것뿐이다 — 사용자 개입 없이 서버가 알아서 재발급할 수 있는 상황을 매번 사용자에게 떠넘기고 있었다.

또한 프론트엔드 `/brokerage/connect` 화면은 `account`가 존재하면 무조건 "이미 연동되어 있습니다 → 대시보드로" 화면만 보여주고 재연동 폼 자체에 접근할 방법이 없었다 — 진짜로 appKey가 만료/취소돼 재연동이 필요한 사용자도 폼에 도달할 수 없는 막다른 골목이었다.

## Decision

1. **토큰 만료 시 자동 재발급** — `BrokerageService.requireCredentials()`가 `isTokenValid()`가 false면 즉시 에러를 던지는 대신, 저장된 appKey/appSecret으로 `BrokerageClient.issueToken()`을 다시 호출해 조용히 갱신한다. 성공하면 사용자는 아무것도 알아챌 필요가 없다.

2. **재발급 실패만 "재연동 필요"로 취급** — 재발급 자체가 실패하면(appKey/appSecret이 실제로 취소·변경된 경우) `BrokerageAccount.authFailedAt`(신규 컬럼)에 실패 시각을 기록하고, 그때부터 진짜 "재연동이 필요합니다" 에러를 사용자에게 보여준다. 성공하면 `authFailedAt`을 다시 null로 지운다.

3. **재시도 쿨다운(5분)** — `authFailedAt`이 5분 이내면 재발급을 다시 시도하지 않고 즉시 에러를 반환한다. 진짜로 취소된 앱키로 매 요청마다 브로커 인증 엔드포인트를 두드리는 걸 막기 위해서다. 5분이 지나면 다시 자동 재시도한다(일시적 네트워크 장애였을 경우 스스로 복구됨). 사용자가 직접 `/brokerage/connect`에서 재연동하면 즉시 `authFailedAt`이 지워진다.

4. **`AccountResponse.tokenValid`의 의미 변경** — 지금까지는 "액세스 토큰이 만료 전인가"였지만, 이제는 "최근 재발급 시도가 실패했는가"(`authFailedAt == null`)로 바뀐다. 정상적인 24시간 주기 만료는 이제 대시보드에 전혀 드러나지 않는다 — 사용자가 신경 쓸 필요가 없는 내부 동작이기 때문이다. `GET /api/brokerage/account`(대시보드 조회)는 그 자체로는 재발급을 시도하지 않는다 — 조회만으로 브로커 API를 호출하는 부작용을 피한다. 실제 재발급은 잔고 조회/주문 제출처럼 자격증명이 실제로 필요한 호출에서만 일어난다(대시보드는 어차피 잔고도 함께 조회하므로 매 방문 시 자연스럽게 갱신 기회를 얻는다).

5. **프론트엔드 재연동 접근 경로 수정** — `/brokerage/connect`는 이제 `tokenValid=false`인 경우 "재인증이 필요합니다" 안내와 함께 연동 폼을 그대로 보여준다(기존 provider/계좌번호가 기본값으로 채워짐). `tokenValid=true`일 때만 기존처럼 "이미 연동됨 → 대시보드" 막다른 화면을 보여준다. 대시보드 상태 카드에도 `tokenValid=false`일 때 "재연동" 버튼을 추가한다.

6. **전용 예외 타입(`ReconnectRequiredException`)** — 처음에는 재연동 필요 상태를 `IllegalStateException`으로 던졌는데, 라이브 테스트로 즉시 500이 새는 걸 확인했다: `GlobalExceptionHandler`의 `IllegalStateException` 처리는 메시지에 "현재가"/"보유"/"잔고"/"불가"/"없음" 중 하나가 있어야만 409로 매핑하고, 그 외엔 500으로 숨긴다("증권사 인증이 만료되었습니다..." 메시지는 이 키워드 중 아무것도 포함하지 않는다). 메시지 내용에 의존하는 휴리스틱은 이렇게 조용히 깨지므로, 전용 예외 타입을 만들어 `GlobalExceptionHandler`에 항상 401로 매핑되는 핸들러를 등록했다. 기존 `requireCredentials()`의 "계좌 정보가 불완전합니다" 케이스도 같은 이유로 500이 새고 있었던 걸 이번에 같이 고쳤다.

## Reasons

- **자동 재발급이 기본이어야 하는 이유**: KIS/Toss 둘 다 refresh token 없이 appKey/appSecret으로 재발급하는 동일 구조라, "24시간마다 사용자가 직접 재연동"은 불필요한 마찰이다 — 이미 가진 정보로 서버가 처리할 수 있는 일을 사용자에게 떠넘기지 않는다.
- **영구 차단 대신 5분 쿨다운**: 완전히 막아버리면(예: 한 번 실패 후 재시도 자체를 영구 중단) 일시적 네트워크 장애·서킷브레이커 OPEN 상황도 사용자가 수동으로 재연동해야 풀리는 상황이 된다. 반대로 매번 무조건 재시도하면 실제로 취소된 앱키에 대해 브로커 인증 엔드포인트를 계속 두드리게 된다. 5분 쿨다운은 두 극단 사이의 실용적 절충이다.
- **`GET /api/brokerage/account`는 재발급을 시도하지 않음**: 단순 조회 화면 로딩만으로 외부 브로커 API를 호출하는 건 놀라운 부작용이다. 잔고/주문처럼 실제로 자격증명이 필요한 호출에서만 재발급이 일어나게 하면, 대시보드는 어차피 잔고도 같이 불러오므로 실질적 사용자 경험 손실 없이 부작용만 줄인다.

## Consequences

- `BrokerageAccount`에 `authFailedAt: Instant?` 컬럼이 추가된다(V36 마이그레이션). 기존 행은 모두 null(정상)로 시작한다.
- 동시성: 같은 계정에 대해 거의 동시에 여러 요청이 들어오면 토큰 만료 직후 재발급 API가 중복 호출될 수 있다 — 사용자 단위 낮은 트래픽에서는 실질적 위험이 낮다고 보고 분산 락은 도입하지 않는다.
- `requireCredentials()`가 이제 부작용(재발급 시 DB 저장)을 가진다 — 기존에는 순수 조회였다. `@Transactional` 메서드 내부에서 호출되므로 트랜잭션 경계는 그대로 유지되지만, **`@Transactional(readOnly = true)`인 메서드에서 호출하면 안 된다** — `getBalance()`가 원래 readOnly였는데, Hibernate가 커밋 시 flush를 건너뛰어 재발급이 매번 로그상으로는 성공했지만 DB에는 결코 반영되지 않는 버그가 라이브 테스트에서 실제로 발생했다(고쳐서 일반 `@Transactional`로 바꿨다). `submitOrder()`처럼 재발급 이후 같은 트랜잭션에서 리스크 게이트가 주문을 막는 경우, 트랜잭션 전체가 롤백되며 방금 성공한 재발급도 함께 사라진다 — 다음 요청에서 다시 재발급을 시도하므로 틀린 동작은 아니지만(자기 복구됨), 불필요한 재시도가 한 번 더 생긴다. 트래픽이 늘면 이 경로만 별도 트랜잭션(REQUIRES_NEW)으로 분리하는 걸 고려한다.
- 정상적인 토큰 만료가 대시보드에서 완전히 보이지 않게 되므로, 실제로 문제가 있을 때만 "재연동" 신호가 뜬다 — 알림 피로(불필요한 경고)가 줄어드는 대신, 재발급이 진행 중이라는 사실 자체는 사용자에게 노출되지 않는다(로그로만 확인 가능).

## Revisit When

- 사용자 트래픽이 늘어나 계정당 동시 재발급 호출이 실제로 관측되면 Redis 기반 단일 비행(single-flight) 락 도입을 검토한다.
- KIS/Toss 중 하나라도 refresh token 방식으로 전환하면 이 ADR의 재발급 로직 전체를 다시 설계해야 한다.
- 5분 쿨다운이 실제 운영에서 너무 짧거나 길다는 게 확인되면(오탐/과탐) 조정한다.
