# ADR-059: 결제 경로의 남은 갭을 닫는다 — 서버가 쥐는 orderId·금액, PENDING 적체 정리, 거절 급증 알림

## Status
Accepted

## Context

[ADR-053](053-payment-idempotency-and-failure-classification.md)이 정기결제의 멱등성과 PG 실패
분류를 정리하면서, 그 Consequences에 **닫지 못한 갭 다섯 개**를 적어뒀고
[launch-plan Phase 4](../launch-plan.md)가 그걸 `PG_MOCK_ENABLED=false` 전환의 블로킹 항목으로
올렸다. 이 ADR은 그중 넷을 닫는다.

| 갭 | 상태 |
|---|---|
| 일회성 결제(confirm)에 서버 생성 orderId | **닫았다** (§1) |
| 갱신 실패·보류 건 재시도 주기 | **닫았다** (§2) |
| PENDING 결제 적체 청소 | **닫았다** (§2) |
| 결제 실패 급증 알림 | **닫았다** (§3) |
| CH-13/14를 토스 실제 테스트 키로 재실행 | **남았다** — 실제 상점 계정이 필요해 코드로 해결할 수 없다 |

작업하면서 두 가지가 더 나왔다. 하나는 결제 우회 취약점이고(§1), 하나는 갱신이 성공해도 원장이
비는 결함이다(§4). 둘 다 이 ADR에서 함께 고친다.

## Decision

### 1. 일회성 결제의 orderId와 금액을 서버가 쥔다

**발견한 취약점부터.** `confirm` 은 `{paymentKey, orderId, amount, planCode}` 를 요청 바디로
받았다. 토스 confirm은 "**보낸 금액이 실제 결제 금액과 같은가**"만 검증한다 — 그 금액이 어떤
플랜의 값인지는 알지 못한다. 그래서:

```
1. 프론트 SDK로 100원 결제          → 토스에 100원 결제가 실재한다
2. POST /confirm {amount:100, planCode:"PRO"}
3. 토스: "100원 결제 맞음" → DONE
4. 우리: PRO 활성화 (plan.price 9900은 기록에만 쓰였다)
```

**9,900원 플랜을 100원에 살 수 있었다.** 금액을 클라이언트가 정하게 두면 PG의 금액 검증은
검증이 아니다 — 클라이언트가 양쪽을 다 정하기 때문이다.

같은 뿌리에서 두 번째 문제가 나온다. orderId도 클라이언트 것이었으므로, ADR-053이 정기결제에
걸어둔 `payment_records.pg_order_id` 유니크 인덱스가 **일회성 결제에서는 지킬 것이 없었다.**
멱등성의 열쇠를 공격자가 쥐고 있으면 DB 제약은 장식이다.

**결정**: 결제 준비 단계를 서버에 둔다.

```
POST /api/subscription/payment/prepare  {planCode}
  → orderId = "sub_<userId>_<uuid>"      (서버 생성)
  → amount  = plan.price                 (서버 고정)
  → PENDING PaymentRecord 저장
  ← {orderId, amount}                    프론트는 이 값으로 SDK를 띄운다

POST /api/subscription/payment/confirm  {paymentKey, orderId}
  → orderId로 기록 조회 (userId 일치 확인 — 남의 orderId는 조회되지 않는다)
  → 기록의 amount를 PG에 보낸다 (클라이언트 금액은 받지도 않는다)
```

`confirm` 요청 바디에서 `amount` 와 `planCode` 를 **없앴다.** 받지 않으면 신뢰할 일도 없다.

**멱등성 두 구멍도 같이 닫힌다.**

- *confirm 중복 수신*: 예전에는 토스가 2회차를 4xx로 거절하고, 우리는 그걸 "결제 실패"로 읽어
  **실제로 성공한 결제에 400을 돌려줬다.** 이제 이미 SUCCESS인 기록은 PG를 찌르지 않고 첫 확정의
  결과를 그대로 재생한다.
- *응답 유실*: confirm이 어떤 이유로든 실패하면 `getPaymentStatus(paymentKey)`로 PG에 되묻고,
  DONE이면서 **금액까지 일치**하면 성공으로 이어간다. 그래야 "돈은 빠졌는데 구독은 없다"가
  생기지 않는다. 금액이 어긋나면 DONE이라도 거절한다 — 위 취약점이 이 경로로 되살아나면 안 된다.

### 2. PENDING 적체를 정리하고, 갱신을 매일 돌린다

ADR-053은 PG 장애·불확정에서 결제를 **FAILED로 굳히지 않고 PENDING으로 남긴다.** 그게 이중청구와
오강등을 막는 유일한 방법이지만, **그 상태를 정리하는 주체가 없었다.** 둘이 썩는다:

1. **실제로 청구된 결제가 PENDING으로 방치된다** — 고객은 돈을 냈는데 구독이 없다.
2. 연속 실패 카운트의 기준(마지막 성공 이후)이 흐려져 강등 판정이 어긋난다.

갱신 배치는 월 1회였고 만료 예정만 보므로 이 역할을 대신할 수 없다.

**결정**: 두 가지를 같이 바꾼다.

- **`paymentReconciliationJob`을 6시간마다 돌린다.** 10분 이상 지난 PENDING을 orderId로 PG에
  되물어 정리한다. DONE → 확정, 확정적 취소 → 실패, 조회 실패 → 그대로 둠,
  권위 있는 "결제 없음" → **72시간이 지난 것만** 실패로 닫는다(그 전에는 갱신이 다시 긁을 수
  있으므로 열어둔다).
- **갱신 배치를 매월 1일 → 매일로.** orderId가 (구독, 청구주기)에서 결정적으로 유도되므로 매일
  돌려도 같은 주기를 두 번 청구하지 않는다. 리더는 `expiresAt <= now + 1일` 만 집어가므로 평소
  실행은 대상 0건이다.

판단 로직은 `SubscriptionService.resolvePendingPayment()` **하나**를 갱신과 정리 배치가 공유한다.
같은 판단을 두 곳에 적어두면 반드시 어긋나고, 어긋나는 쪽이 돈이다.

### 3. 거절 급증을 알림으로 잡는다

ADR-053에서 **4xx를 서킷브레이커 집계에서 일부러 뺐다** — 복구 경로의 첫 동작이 orderId 조회이고
정상 답이 404라서, 그걸 세면 복구가 자기 브레이커를 열어버린다. 그 대가로 "PG는 멀쩡한데 결제가
전부 거절된다"를 브레이커가 못 잡게 됐다. ADR-053 Consequences가 그걸 알림으로 잡으라고 적었다.

`payment_records`는 테이블이고 알림은 메트릭을 본다. 그 사이를 `payment_result_total{kind}`
카운터로 메운다 — 라벨 축은 `PaymentFailureKind`와 같다(`success`/`declined`/`unavailable`/
`indeterminate`). 거절과 장애를 섞으면 알림이 무엇을 말하는지 알 수 없다. 대응이 정반대다.

| 알림 | 조건 | 왜 |
|---|---|---|
| `PaymentDeclineRateHigh` | 15분간 거절 5건 초과 **이면서** 비율 50% 초과 | 키 만료·상점 설정 변경·PG 스펙 변경. 결제량이 적은 시간대에 한두 건으로 깨우지 않으려 비율과 절대량을 함께 본다 |
| `PaymentIndeterminateGrowing` | 1시간간 불확정 3건 초과 | 정리 배치(6시간 주기)가 유입을 따라가지 못한다는 신호 |

카운터는 **첫 증가 때 생긴다.** 미리 0으로 등록하지 않으면 결제가 없는 동안 시계열이 아예 없어
비율 알림이 "데이터 없음"으로 조용히 통과한다 — `OutboxBacklog`·`SagaIncomplete`가 게이지에
`_total`을 붙여 빈 시계열을 보고 있었던 것과 같은 실패 모드다(resilience-plan §4.6). 네 종류를
전부 0으로 선등록하고, `PaymentMetricsTest`가 메트릭 이름과 라벨 값을 계약으로 고정한다.

### 4. 성공 경로를 하나로 모은다 — 갱신 원장 누락

§2를 구현하다 발견했다. 결제 성공을 확정하는 코드가 **세 곳**에 흩어져 있었고
(`activatePaidPlan` / 갱신 성공 / 불확정 복구), 각자 `markSuccess` + `extend` 를 했다.
**원장 기록은 그중 일회성 경로에만 있었다.**

즉 **정기결제가 성공해도 `SUBSCRIPTION_PAYMENT` 원장 행이 생기지 않았다.** 돈은 움직이고 회계는
빈다. `bench/consistency/verify.py`의 "성공 결제 수 == 원장 행 수" 불변식이 정확히 이걸 잡으려고
있는 것인데, **갱신 배치가 한 번도 돌지 않았기 때문에**(ADR-053에서 발견) 드러날 기회가 없었다.
불변식을 써두는 것만으로는 부족하고 그 경로가 실제로 실행돼야 한다는 증거다.

세 경로를 `settlePayment()` 하나로 모았다 — 기록 확정·메트릭·원장·구독 연장을 한 번에 한다.

## Reasons

**왜 금액을 기록에서 읽는가(플랜 가격이 아니라).** 준비 시점에 고정된 값이 과금의 근거다. 그
사이 플랜 가격이 올랐더라도 고객이 실제로 낸 금액은 기록 쪽이고, 원장은 실제로 받은 돈을 적어야
한다.

**왜 confirm에서 `planCode`를 없앴는가.** orderId가 기록을 가리키고 기록이 플랜을 안다. 같은
정보를 두 경로로 받으면 어긋날 수 있고, 어긋났을 때 어느 쪽을 믿을지에 대한 답이 "클라이언트"면
안 된다.

**왜 "결제 없음"을 즉시 닫지 않는가.** 그 순간에는 청구되지 않았다는 뜻일 뿐이고, 갱신 배치가
같은 orderId로 다시 긁을 수 있다. 즉시 FAILED로 닫으면 연속 실패 카운트가 늘어 오강등으로
이어진다 — ADR-053이 막은 바로 그 경로다. 72시간은 "사람이 눈치챌 시간"이지 기술적 근거가 있는
값은 아니다(§Revisit).

**왜 갱신을 매일 돌리는가.** 보류된 건이 다음 기회를 한 달 기다리는 것이 유일한 대안이었다.
멱등성이 확보된 뒤에는 자주 돌리는 쪽의 비용이 거의 없다 — 대상이 없으면 읽을 것도 없다.

## Consequences

**준비만 하고 결제하지 않은 PENDING이 쌓인다.** `/prepare`를 호출하고 SDK를 닫아버리는 경우다.
72시간 뒤 정리 배치가 닫지만, 그때까지는 그 사용자의 "마지막 성공 이후 실패 건수"에 영향이
없더라도 적체로는 보인다. `/prepare`에 시간당 20회 레이트리밋을 걸어 양을 제한했을 뿐,
**구조적으로 막지는 않았다.**

**프론트엔드는 아직 이 경로를 쓰지 않는다.** 웹은 정기결제 위젯만 연동돼 있고 일회성 결제는
`/subscribe`(Mock PG)를 탄다. `/prepare` → SDK → `/confirm` 흐름을 프론트에 연결하는 작업이
남아 있고, **그래서 이 경로는 실제 브라우저에서 한 번도 돌아본 적이 없다** — 단위 테스트와
스텁 PG까지만 검증됐다.

**72시간·10분·6시간은 다 짐작이다.** 실제 PG 장애의 지속 시간 분포를 본 적이 없다. 프로퍼티로
빼뒀으니 운영 데이터가 생기면 바꿀 수 있지만, 지금 값에 근거는 없다.

**알림 임계(50%, 5건, 3건)도 짐작이다.** 결제량 기준선이 없는 상태에서 정한 값이라, 라이브
전환 후 첫 몇 주는 오탐·미탐을 보며 조정해야 한다.

**`settlePayment`가 구독 행이 없으면 연장을 건너뛴다.** 적체 정리 경로에서 구독이 그 사이 해지된
경우인데, 그러면 결제는 SUCCESS로 확정되고 원장에도 적히지만 구독은 복구되지 않는다. 환불이
필요한 상황이고, **그 판단을 자동화하지 않았다** — 사람이 봐야 한다. 지금은 로그만 남는다.

## Revisit When

- 토스 실제 테스트 키로 CH-13/14를 재실행할 때 — 남은 갭 하나이고, 이 ADR의 `getPaymentStatus`
  금액 비교와 404 동작이 실제 응답과 맞는지 그때 확인된다
- 프론트에 `/prepare` → SDK → `/confirm` 흐름을 연결할 때 — 그때 비로소 §1이 실제로 검증된다
- 라이브 전환 후 결제량 기준선이 생길 때 — 알림 임계와 72시간/10분/6시간을 실측으로 교체
- PENDING 적체가 꾸준히 늘 때 — `/prepare` 남발을 구조적으로 막아야 한다는 신호
- 해지된 구독의 결제가 확정되는 사례가 나올 때 — 자동 환불 정책을 결정해야 한다
